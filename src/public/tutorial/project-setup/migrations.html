Migrations: users, books, authors, author_book, reviews

Creating and running the migrations for the full schema, one table at a time: naming, column/foreign-key syntax, and the migrate command's rollback mechanics.

The last topic's closing paragraph already told you what a migration is — a version-controlled PHP class describing one schema change, applied by php artisan migrate rather than hand-edited in phpMyAdmin. This topic puts that into practice for real: four new tables, books, authors, author_book, and reviews, each one kept as its own individually runnable, individually reversible step.

Naming: timestamps set the order

Every migration file starts with a full timestamp — 2026_09_12_065917_create_books_table.php — because php artisan migrate runs pending migrations in filename order, and a timestamp sorts exactly the way it happened chronologically. That's also why the three default migrations you already have look the way they do: 0001_01_01_000000_create_users_table.php and its two siblings use a deliberately tiny, made-up timestamp — year 0001 — guaranteeing they sort before literally any migration a real project ever generates, since users has to exist before anything that references it.

You get a correctly-timestamped file for free by generating it rather than creating one by hand:

php artisan make:migration create_books_table

This writes an empty stub straight into database/migrations/, timestamp already filled in, ready to edit:

Schema::create('books', function (Blueprint $table) {
    $table->id();
    $table->timestamps();
});

Running that same command three more times — for create_authors_table, create_author_book_table, and create_reviews_table, in that order — gives four stubs whose timestamps already reflect the order this schema needs: author_book references both books and authors, and reviews references books and users, so both have to come after the tables they point at.

Writing each table

books

Schema::create('books', function (Blueprint $table) {
    $table->id();
    $table->string('title');
    $table->text('description')->nullable();
    $table->year('year');
    $table->string('image')->nullable();

    // Part 1 keeps one implicit edition per book, rather than a
    // separate editions table - these four fields describe that
    // one edition directly.
    $table->string('isbn')->nullable();
    $table->string('publisher')->nullable();
    $table->string('edition_number')->nullable();
    $table->decimal('price', 8, 2)->nullable();

    $table->timestamps();
});

Most of this reads directly off your SQL knowledge: string is VARCHAR(255), text is TEXT, decimal(8, 2) is exactly the SQL type of the same name. year() is one you might not have reached for by hand — MySQL has a dedicated YEAR type, and this is the column it's for. $table->id() is the one genuinely new piece: an auto-incrementing BIGINT UNSIGNED primary key named id, which is also the column every foreignId() below assumes it's pointing at.

authors

Schema::create('authors', function (Blueprint $table) {
    $table->id();
    $table->string('name');
    $table->string('image')->nullable();
    $table->text('bio')->nullable();
    $table->timestamps();
});

No foreign keys yet — an Author doesn't belong to anything else. The relationship between books and authors lives in the next table instead.

author_book

Schema::create('author_book', function (Blueprint $table) {
    $table->id();
    $table->foreignId('book_id')->constrained()->onDelete('cascade');
    $table->foreignId('author_id')->constrained()->onDelete('cascade');
    $table->timestamps();
});

A Book can have many Authors, and an Author can have written many Books — a many-to-many relationship, which needs a table in between holding pairs of IDs. author_book is exactly that join table, named the way Laravel expects: the two related table names, singular, alphabetical, joined with an underscore. $table->foreignId('book_id') on its own just adds a BIGINT UNSIGNED column named book_id; ->constrained() is what turns it into a real foreign key — it works out, from the column's own name, that book_id should reference books.id. Running SHOW CREATE TABLE author_book afterward shows exactly the constraint you'd expect to have written by hand:

CONSTRAINT `author_book_book_id_foreign` FOREIGN KEY (`book_id`) REFERENCES `books` (`id`) ON DELETE CASCADE,
CONSTRAINT `author_book_author_id_foreign` FOREIGN KEY (`author_id`) REFERENCES `authors` (`id`) ON DELETE CASCADE

->onDelete('cascade') on both means deleting a Book or an Author also deletes the pairing rows that mentioned it — without it, that delete would simply fail with a foreign-key-constraint error instead, since a dangling author_book row referencing a Book that no longer exists isn't allowed.

reviews

Schema::create('reviews', function (Blueprint $table) {
    $table->id();
    $table->foreignId('book_id')->constrained()->onDelete('cascade');
    $table->foreignId('user_id')->constrained()->onDelete('cascade');
    $table->unsignedTinyInteger('rating');
    $table->text('comment')->nullable();
    $table->timestamps();

    // At most one review per user per book - enforced here, not
    // just in application code.
    $table->unique(['book_id', 'user_id']);
});

rating only ever needs to hold 1–5, so unsignedTinyInteger — SQL's smallest integer type — is a better fit than a plain integer; nothing about the app changes if the column happens to be smaller than it needs to be, but it's worth picking the type that actually matches the data. The last line is doing real work: a unique composite index across two columns together, so the pair (book_id, user_id) can't repeat — one row per user for a given book is fine, and one row per book for a given user is fine, but the same user reviewing the same book twice would violate the index and fail at the database level, not just get caught by a validation rule that a bug could bypass.

Running the migrations

php artisan migrate runs every migration that hasn't run yet, in filename order, and records each one in a migrations table of its own — that's how it knows, next time, which files are already applied and which are still pending. Run plain, all four new tables would go in one call:

$ php artisan migrate

   INFO  Running migrations.

  2026_09_12_065917_create_books_table .......................... 60ms DONE
  2026_09_12_065936_create_authors_table ........................ 56ms DONE
  2026_09_12_065948_create_author_book_table ................... 531ms DONE
  2026_09_12_070000_create_reviews_table ....................... 476ms DONE

Every migration that runs together in one call like this shares a batch number — which matters for rolling back, covered next. Adding --step changes that: each migration that runs gets recorded as its own batch, even several at once in a single command:

$ php artisan migrate --step

php artisan migrate:status shows the difference plainly. The three default migrations were all applied together at first-time setup, with no --step — batch 1, all three. This lesson's four ran with --step, in one call, and still landed in batches 2 through 5, one table each:

$ php artisan migrate:status

  Migration name .............................................. Batch / Status
  0001_01_01_000000_create_users_table ............................... [1] Ran
  0001_01_01_000001_create_cache_table ............................... [1] Ran
  0001_01_01_000002_create_jobs_table ................................ [1] Ran
  2026_09_12_065917_create_books_table ................................ [2] Ran
  2026_09_12_065936_create_authors_table ............................... [3] Ran
  2026_09_12_065948_create_author_book_table ........................... [4] Ran
  2026_09_12_070000_create_reviews_table ................................ [5] Ran

Undoing a migration

Every migration file has a down() method alongside up() — for books, that's just Schema::dropIfExists('books'). php artisan migrate:rollback uses it to undo migrations — by default, the most recent batch:

$ php artisan migrate:rollback

   INFO  Rolling back migrations.

  2026_09_12_070000_create_reviews_table ......................... 96ms DONE

Because reviews was its own batch, this undoes exactly that one table. Without --step on the way in, several migrations sharing a batch would all roll back together here instead — not what you'd want if only the newest one actually needs undoing.

migrate:rollback takes its own --step too, and it means something more precise than "batches": --step=N walks back the last N migrations individually, in reverse order, regardless of which batch each one landed in:

$ php artisan migrate:rollback --step=2

   INFO  Rolling back migrations.

  2026_09_12_065948_create_author_book_table .................... 102ms DONE
  2026_09_12_065936_create_authors_table ......................... 17ms DONE

That undoes author_book and authors — the two most recently run migrations — leaving books (and everything before it) untouched, batch number aside. Running php artisan migrate (with or without --step) again re-applies whatever's pending, in the same filename order as always.

One more command worth knowing, mainly for your own local experimenting: php artisan migrate:fresh drops every table outright and re-runs every migration from scratch — a clean slate, useful when your local database has gotten into a state you'd rather just discard than debug. It's not something you'd run against data anyone cares about keeping.

One rule from here on

These four files are the schema for the rest of this course. Once a lesson is finished and tagged, its migrations are never edited again to fix a mistake — a correction becomes a new migration instead, the same way you'd never rewrite a query that already ran against production data. Nothing about this course has reached that point yet, but it's the reason migrations are written the way they are: each one a small, standalone, one-directional step, not a file you come back to and adjust.
