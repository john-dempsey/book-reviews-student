The Laravel application structure

A guided tour of the bare install: URL rewriting and the front controller, MVC at a glance, routing, where Models/Controllers/Views live, the public folder, the database folder and .env, and how tests fit in.

Before writing any app-specific code, it's worth knowing the shape of what laravel new . already gave you, and how a request actually travels through it. Everything on this page already exists in src/ right now — you're touring, not building yet. That starts with the next topic.

URL rewriting: one file answers every request

In the prior PHP module, a URL usually pointed at a real .php file on disk — /about.php served about.php. Laravel doesn't work that way. Apache's document root points at src/public/, and that folder contains an .htaccess file with a rewrite rule at the bottom of it:

RewriteCond %{REQUEST_FILENAME} !-d
RewriteCond %{REQUEST_FILENAME} !-f
RewriteRule ^ index.php [L]

Read as English: if the requested path isn't a real directory and isn't a real file, rewrite it to index.php instead. So /books, /books/3, and /anything-that-doesn't-exist-as-a-file all end up running the exact same PHP file — public/index.php, Laravel's front controller. Its actual job is short:

$app = require_once __DIR__.'/../bootstrap/app.php';

$app->handleRequest(Request::capture());

It boots the framework, hands it the incoming request, and lets Laravel decide what to do with it. Nothing about which code runs is decided by the URL rewriting itself — that's the router's job, covered next. The rewrite rule's only job is making sure every request that isn't a real file gets to Laravel at all.

MVC, at a glance

Laravel is a Model-View-Controller framework — not by forcing rigid separation, but by giving each part its own folder and convention:

  • A Model represents one thing your data cares about (a Book, a Review) and knows how to load and save its own rows. You've written something in this shape by hand already.
  • A View turns data into the actual HTML response — a Blade template here, not plain PHP echo statements.
  • A Controller sits between the two: a request arrives, the Controller asks a Model for whatever data it needs, then hands that data to a View to render.

Strung together, one request looks like this:

Browser → routes/web.php → Controller → Model (talks to the database)
                                ↓
                             Blade View → HTML back to the browser

The router decides which Controller (or closure) handles a given URL — that's the piece still missing from the picture above.

Routing: where a URL is decided

routes/web.php is where a URL pattern gets matched to the code that handles it. Right now, it holds exactly one route:

Route::get('/', function () {
    return view('welcome');
});

Route::get() matches GET requests to the given path (/); the second argument is what runs when it matches — here, a closure that returns a View directly. Once there's a real Controller worth calling, that second argument becomes a reference to one of its methods instead of an inline closure — you'll see that shift happen later in this lesson, once Breeze and this app's own Controllers exist. (routes/console.php also exists, for defining custom artisan commands — nothing in this course uses it.)

Where things live

Folder What lives there What's already there
app/Models/ Eloquent model classes, one per database table User.php
app/Http/Controllers/ Controller classes Controller.php — an empty base class every controller will extend
resources/views/ Blade templates (.blade.php) welcome.blade.php
routes/web.php Maps URLs to closures or controller methods The one route above
database/migrations/ One file per schema change, applied in order users, cache, jobs
config/ One PHP file per subsystem, each reading its values from .env database.php, among many others
public/ Anything Apache serves directly index.php, plus the static content below
artisan Laravel's command-line entry point — a single file, not a folder Every php artisan ... command runs through it

Almost all of the code you write for the rest of this course lands in the first four rows.

The artisan CLI

artisan is the file behind every command-line interaction you'll have with Laravel this course: php artisan migrate (mentioned at the end of the last topic), php artisan make:model, php artisan tinker for poking at models interactively, and more as the course goes on. It isn't a folder holding code you'll write yourself — it's the command-line interface, dispatching to code that already exists inside the framework or your own app. You'll always run it from the workspace container's terminal, never from your own machine directly.

The public folder and static content

public/ is the one folder Apache's document root points at directly — anything in it is reachable by URL, whether or not Laravel is involved. index.php is the front controller from earlier; alongside it sit files Apache just serves as-is, with no PHP and no routing: favicon.ico, robots.txt, and public/build/, where Vite drops the compiled CSS/JS once Breeze's asset pipeline is running.

There's a concrete example one click away: the tutorial site you're reading right now is a folder of plain HTML and CSS sitting at public/tutorial/. It didn't come through a route or a Controller — Apache found a real file on disk at the requested path and served it directly, the same way it would serve favicon.ico. That's the whole distinction between "static content" and "the app": whether the request finds a real file in public/ first, or falls through to index.php.

The database folder and .env

database/migrations/ is where the migrations mentioned at the end of the last topic actually live — right now, just the three Laravel ships by default (users, cache, jobs). database/factories/ and database/seeders/ exist too, holding only the default UserFactory for now; you won't touch either folder for real until Lesson 2.

Laravel reads its database connection details from .env, not from a config file you'd edit directly:

DB_CONNECTION=mysql
DB_HOST=mysql
DB_DATABASE=book_reviews
DB_USERNAME=laravel

config/ is where those .env values actually get consumed — one PHP file per subsystem (app.php, database.php, session.php, and more), each reading env() calls into plain PHP arrays that the rest of Laravel uses. config/database.php specifically is the bridge for the block above, and it's why changing a DB_* value in .env changes which database php artisan migrate talks to, with no other file to edit. DB_HOST=mysql here is the same mysql-container you saw running in phpMyAdmin in the last topic — this .env is how Laravel knows to look for it there instead of on your own machine.

Testing

tests/ splits into tests/Unit/ and tests/Feature/, both extending the shared tests/TestCase.php. Unit tests check one class in isolation — a model's relationships, for example; feature tests make real HTTP requests against a route and check the response, closer to how a browser would actually use the app. Both run against the same MySQL database the app itself uses — there's no separate, lighter test database here — with the RefreshDatabase trait resetting it between tests so one test's data never leaks into the next.

Right now tests/ is essentially empty — this lesson's first real tests are its very last topic, once there's an actual schema and actual models worth testing.
