Validation and form repopulation

$request->validate() replaces the hand-written validator class and manual PRG flow from the PHP module - rule strings, automatic redirect-back-with-errors on failure, and old()/@error in Blade.

Last topic ended on a raw database error: leave title blank, submit the form, and MySQL's own NOT NULL constraint is the only thing that noticed. That's not something any real user should ever see. This topic fixes it - and it's the closest this course gets to "you've already built this," because it has already been built once, by hand, in the PHP module.

The same job, done there already

That prior module had a hand-written validator class, and a PRG (Post-Redirect-Get) flow built around it: check the submitted values, and if any failed, redirect back to the form instead of rendering a result page directly, carrying the error messages and the values already typed in along with it - so the user lands back on a form that still has their input, with a message next to whatever was wrong. Laravel's validation does exactly that job. The mechanism is different - a rule-string array instead of a hand-written check - but the goal, and the redirect-back-with-everything-attached shape of it, is the same thing already built once.

$request->validate()

$validated = $request->validate([
    'title' => 'required|string|max:255',
    'description' => 'nullable|string',
    'year' => 'required|integer|digits:4',
    'isbn' => 'nullable|string|max:255',
    'publisher' => 'nullable|string|max:255',
    'edition_number' => 'nullable|string|max:255',
    'price' => 'nullable|numeric|min:0',
]);

Each key is a field name from the form; each value is a list of rules, separated by |. required rejects a missing or blank value; nullable says the opposite - blank is fine, but if something is there, the rules after it still apply; max:255 and digits:4 bound length; integer/numeric reject non-numbers. There's no loop, no if, no hand-written message string anywhere in this method - the rule strings are the validator.

When every rule passes, validate() returns the validated data as an array - $validated here - and the method carries on to the next line, exactly as before. Book::create($validated) replaces last topic's Book::create($request->all()): $fillable was already filtering the keys down to safe columns, and now $validated filters the values too, so both problems - the wrong keys reaching the database, and the wrong values - are covered before the INSERT ever runs.

When a rule fails

When any rule fails, validate() never returns at all. It throws an exception, and Laravel's own exception handling middleware catches that specific one and does the entire PRG flow automatically: redirect back to the previous page (the form store() was called from), with the validation errors flashed to the session, and every submitted field flashed alongside them. Nothing in BookController@store has to ask for any of that - it's already done by the time the response reaches the browser.

That's the same shape as redirect()->back()->withErrors()->withInput(), written out by hand once in the PHP module - validate() just does it for you on failure, rather than making the controller call it explicitly.

Reading the flash data back: old() and @error

Two things now need to appear in books/create.blade.php: the error message next to whatever field was wrong, and that field's own previously-submitted value, so the user doesn't have to retype the six fields they got right along with the one they didn't.

<div>
    <x-input-label for="title" :value="__('Title')" />
    <x-text-input id="title" name="title" type="text" class="mt-1 block w-full" value="{{ old('title') }}" required autofocus />
    <x-input-error :messages="$errors->get('title')" class="mt-2" />
</div>

old('title') reads whatever was flashed to the session under that key, or an empty string if there's nothing flashed yet - the same value on a first visit to the form and after a failed submission, just empty in the first case. $errors is a variable Laravel makes available to every view automatically, whether or not the current request actually failed validation; ->get('title') returns that field's messages as an array, or an empty array when there aren't any - x-input-error (a small component already used elsewhere in the app, just not explained until now) renders nothing at all when it's handed an empty array. Every field in the form gets the same two additions - value="{{ old('...') }}" on its input, x-input-error underneath it - none of it new beyond the first field.

Trying it out

Submit the form with title blank now, and the exception, the 500 page, and the raw SQLSTATE message are all gone - the response is a redirect straight back to /books/create, with "The title field is required." under the title box and every other field exactly as it was typed. Submit it correctly, and nothing about last topic's behaviour changed at all: the book saves and the browser lands on its show page.

year is worth trying deliberately, too: type abc instead of a number, and integer catches it the same way required caught the blank title - a message next to the field, everything else preserved. That one wasn't reachable at all last topic, since the browser's own type="number" input already blocks non-numeric typing in most cases - but a request never has to come from a browser obeying its own form's constraints, so the server-side rule matters regardless of what the <input> claims to restrict.
