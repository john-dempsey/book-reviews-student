Author, year, and the limits of LIKE

Widening scopeSearch() to also match an author's name and a book's year - orWhereHas(), a grouped where() closure to keep the OR conditions from leaking into the rest of the query, and a short look at what LIKE can't do.

Topic 5.1 left one gap open on purpose: the search box only ever looked at books.title. Searching for an author's name found nothing, even when that author really had written a seeded book. This topic closes that gap - the same search box, one query scope widened to look in two more places - and then stops to name what still wouldn't work even after that, since a LIKE query was never going to be the last word on search.

Widening the scope

public function scopeSearch(Builder $query, ?string $term): Builder
{
    if (! $term) {
        return $query;
    }

    return $query->where(function (Builder $query) use ($term) {
        $query->where('title', 'like', '%'.$term.'%')
            ->orWhereHas('authors', fn (Builder $query) => $query->where('name', 'like', '%'.$term.'%'));

        if (is_numeric($term)) {
            $query->orWhere('year', $term);
        }
    });
}

The blank-term guard at the top is untouched from topic 5.1 - still the first thing checked, still what makes ->search($term) safe to chain onto every request. Everything new lives inside the where(function ...) closure that now wraps the old where('title', ...) call.

orWhereHas('authors', ...) is the relationship version of the orWhere this app has already used for a simple column - Book doesn't have an author's name as one of its own columns, only a belongsToMany relationship to Author, so matching against it means asking "does this book have any author whose name matches?" rather than comparing a column directly. The closure passed in (fn (Builder $query) => ...) runs against a query on Author, not Book - inside it, 'name' refers to authors.name, the same way 'title' outside it refers to books.title.

The is_numeric($term) check guards the year match for a reason title and name don't need: year is a genuine numeric column, and comparing it against a term that isn't a number at all ('Herbert', say) is a comparison SQL would happily attempt and Laravel would happily send, but one that can never usefully match anything. Skipping it when the term obviously isn't a year is about not asking a pointless question, not about correctness - orWhere('year', 'Herbert') wouldn't break anything by matching, it would just never match, so there'd be no bug from leaving it out. It's also why the year match is orWhere('year', $term)

  • an exact match - rather than the LIKE '%...%' pattern title and name use. A year is one specific number a person is thinking of when they type it, not a phrase someone might remember only part of; matching "196" against every year that merely contains those digits (1960, 1961, ..., 1968, 1969, but also 2196 if this catalogue ever grew that old) would find noise, not the book being searched for.

Why the whole thing sits inside one where()

The outer where(function (Builder $query) use ($term) { ... }) isn't decoration - it's what keeps three orWhere-flavoured conditions from escaping the scope entirely. Eloquent (and the SQL underneath it) reads where(...)->orWhere(...)->orWhere(...), all directly on the same query, as one flat chain: anything else already added to that query becomes one more term the OR reaches across, not something the search terms are jointly required to also satisfy. Nothing in BookController@index currently adds another condition alongside ->search(...), so this scope would happen to return the right rows either way, today. But a scope's whole purpose is to be reusable from any query touching Book - the moment something else adds, say, a ->where('year', '>', 2000) filter to some other page that also calls ->search($term), an ungrouped orWhereHas or orWhere('year', ...) would silently OR its way past that filter instead of narrowing within it. Wrapping the three conditions in one where(function ...) closure forces the SQL to parenthesize them together - WHERE (title LIKE ? OR ... OR year = ?) - so the whole group behaves as a single condition that any other where() on the query still applies alongside, not around.

The search box's label

<input type="search" name="search" value="{{ request('search') }}" placeholder="Search by title, author, or year..."

Nothing about the form itself changed - same GET, same value="{{ request('search') }}", same conditional "Clear" link. Only the placeholder text needed updating, since the box now genuinely searches all three.

Trying it out

Reusing topic 5.1's pinned example, this time giving it a real author and year too:

> $book = \App\Models\Book::factory()->create(['title' => 'Dune', 'year' => 1965]);
> $book->authors()->attach(\App\Models\Author::factory()->create(['name' => 'Frank Herbert']));

Searching /books?search=Herbert now finds Dune even though the word "Herbert" appears nowhere in its title - the match came from orWhereHas('authors', ...) instead. Searching 1965 finds it too, this time from the numeric orWhere('year', ...) branch. Searching Dune still works exactly as it did in topic 5.1 - the original title branch never went away, it just gained two neighbours inside the same grouped where().

What a real search feature would still need

Widening LIKE to two more columns is more coverage, not a different kind of search - every limitation topic 5.1 named is still there, just harder to notice with three columns to try instead of one:

  • No relevance ranking. A search for "the" would match a large fraction of any real catalogue's titles and descriptions, all returned in the same orderBy('title') order regardless of how well each one actually matches - there's no notion of how good a match is, only whether one exists at all.
  • No tolerance for a typo. Searching "Herburt" finds nothing, even though a human reading it would recognise the name instantly. LIKE compares characters, not meaning.
  • No index to make it fast. A LIKE '%term%' with a wildcard on both sides can't use a standard database index the way WHERE id = ? or even LIKE 'term%' (wildcard on one side only) can - the database has no choice but to check every row. Fine at twenty seeded books; a real catalogue of hundreds of thousands would feel it.

Solving any of these for real is a job for a dedicated search tool built for exactly this - Laravel's own Scout package, backed by something like MySQL/PostgreSQL full-text indexes, Meilisearch, or Algolia - rather than more clauses bolted onto a query scope. That's deliberately out of scope here: Lesson 5's job was a flavour of what search involves (a query scope, a GET form, keeping a term alive across pagination), not a production-grade search feature.
