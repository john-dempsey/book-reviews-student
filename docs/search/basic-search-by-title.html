Basic search by title

A search box on books.index, backed by a query scope on Book - the first reusable, chainable piece of query logic this app has written on a model itself, plus withQueryString() to keep a search term alive across pagination links.

Twenty seeded books already spill across two pages of the catalogue. Browsing to find one specific title means scanning cards, page after page - fine at twenty, unworkable at two hundred. This topic adds the first way around that: a search box on books.index that narrows the list down to books whose title actually matches what was typed.

A query scope on Book

Every query this app has written so far has lived inside a controller - Book::with('authors')->withCount('reviews')... in BookController@index, auth()->user()->reviews()->with('book')... in ReviewController@mine. A query scope is a small piece of that same kind of logic, written once on the model instead, so any query touching Book can reuse it by name:

public function scopeSearch(Builder $query, ?string $term): Builder
{
    if (! $term) {
        return $query;
    }

    return $query->where('title', 'like', '%'.$term.'%');
}

The scope prefix is a naming convention Eloquent looks for, not just a label - defining scopeSearch() is what makes ->search($term) callable on any Book query, the same way defining authors() as a relationship is what makes ->authors and ->authors() both work. The early return matters as much as the where() itself: a blank or missing search term leaves the query exactly as it was handed in, untouched. That's what makes ->search($term) safe to chain onto every request to this page, not just ones where a term was actually typed - nobody visiting /books with no search box filled in should see an empty page.

where('title', 'like', '%'.$term.'%') is plain SQL LIKE, wrapped in % on both sides so the term can match anywhere in the title, not just the start - typing "sea" should still find a book called "The Restless Sea". It's also the simplest possible kind of matching: no ranking by relevance, no tolerance for a typo, no understanding of word boundaries. That trade-off is fine at twenty books and worth naming as a trade-off - the next topic comes back to what a real search feature would need instead.

Wiring it into BookController@index

public function index(Request $request)
{
    $books = Book::with('authors')
        ->withCount('reviews')
        ->withAvg('reviews', 'rating')
        ->search($request->query('search'))
        ->orderBy('title')
        ->paginate(12)
        ->withQueryString();

    return view('books.index', compact('books'));
}

->search($request->query('search')) slots straight into the same chain with(), withCount(), and withAvg() already built - a scope returns a query builder exactly like every other method in that chain does, so nothing about how it composes with the rest is new. $request ->query('search') reads the search key from the URL's query string specifically (/books?search=...), rather than $request->input(), which would just as happily read a same-named field from a POST body - worth being explicit about here, since the form below is a GET.

->withQueryString() is new, and solves a problem pagination alone doesn't: without it, clicking through to page 2 of a search's results would carry the page number but silently drop the search term, landing back on page 2 of the entire catalogue instead. withQueryString() tells the paginator to carry every current query string parameter - search included - onto every link it builds.

The search box, and staying on the page you searched

<form method="GET" action="{{ route('books.index') }}" class="mb-6 flex gap-3">
    <input type="search" name="search" value="{{ request('search') }}" placeholder="Search by title...">

    <button type="submit">{{ __('Search') }}</button>

    @if (request('search'))
        <a href="{{ route('books.index') }}">{{ __('Clear') }}</a>
    @endif
</form>

method="GET" matters here in a way it hasn't for any other form in this app - every create/update form so far has been a POST (or a spoofed PUT/PATCH), because submitting one is supposed to change something. Searching doesn't change anything, and a GET request is what makes the result a real, shareable URL - /books?search=Dune can be bookmarked, pasted to someone else, or reached by pressing the browser's back button, none of which a POST result ever manages. That's also why there's no @csrf here: CSRF protection exists to stop a forged request from changing something on a user's behalf, and a GET request that only reads data isn't something Laravel asks for a token on.

value="{{ request('search') }}" is the same repopulation idea topic 3.2 introduced for old() on a failed form submission, aimed at a different source - request('search') reads straight from the current URL's query string, so the box shows whatever was just searched for instead of clearing itself out after every submit. The @if (request('search')) link only appears once a search is active, giving a one-click way back to the unfiltered catalogue.

Trying it out

Every seeded book's title is Faker-generated Latin, the same random text BookFactory has always produced - fine for filling a catalogue, useless for searching against by name, since it's different on every reseed. Topic 2.1 already covered pinning one attribute while leaving the rest to Faker (Book::factory()->create(['title' => 'Dune'])) as "handy when a test cares about one specific value (a known title to search for, say)" - exactly the situation now. In tinker:

> \App\Models\Book::factory()->create(['title' => 'Dune']);

Typing "Dune" into the search box and submitting narrows the catalogue down to that one book, with the box still showing "Dune" rather than resetting to blank. Typing something no title contains at all - "zzz", say - shows a message in its place instead: "No books match "zzz"." rather than the plain "No books in the catalogue yet." message an actually-empty catalogue would show; those are two different situations, and the empty state now says which one happened.

What this can't do yet is anything beyond a title. AuthorSeeder gives every seeded author a real, Faker-generated name of their own (unlike book titles, never pinned to anything fixed) - open authors in phpMyAdmin, pick any one of those five names, and search for it on /books. Nothing comes back, even though that author really did write one of the seeded books - the query never looks anywhere near the authors table, only books.title. That's next topic's job: extending the very same search box to look at an author's name and a book's year too, and a short look at what a search feature could grow into beyond that.
