Create and store

BookController@create and @store - the first form this course writes by hand, @csrf, and route model binding run in reverse to redirect straight to the book that was just created.

The catalogue can be browsed now, but it can't be changed - every book in it arrived through a seeder, not through the app itself. This topic adds the first way to change that: a form for adding a book, and the controller code that saves what it submits. Editing, deleting, and actually checking that submitted values make sense are still to come - this topic only covers getting a new book from a form into the database at all.

Two more routes: create and store

Route::resource() and ->only() are both already familiar from the last lesson - this is just the same line, with two more method names added to the list:

Route::resource('books', BookController::class)->only(['index', 'show', 'create', 'store']);

create registers GET /books/create, named books.create - a page showing a form. store registers POST /books, named books.store - where that form submits to. Both were always part of what Route::resource() offers; last topic's ->only() just hadn't asked for them yet.

BookController@create: showing the form

public function create()
{
    return view('books.create');
}

Nothing more to it than that - the interesting part is the view.

The form itself, and a directive that's new: @csrf

books/create.blade.php is a plain HTML form, styled with the same x-input-label and x-text-input components Breeze's own login and registration forms already use - a hand-written form gets the rest of the app's look for free, rather than needing its own styling invented from scratch:

<form method="POST" action="{{ route('books.store') }}" class="space-y-6">
    @csrf

    <div>
        <x-input-label for="title" :value="__('Title')" />
        <x-text-input id="title" name="title" type="text" class="mt-1 block w-full" required autofocus />
    </div>

    <!-- description, year, isbn, publisher, edition_number, price follow the same shape -->
</form>

@csrf is new: it renders a hidden input carrying a random token, regenerated per session. Every POST/PUT/PATCH/DELETE request in this app passes through a piece of middleware that checks for a token matching the current session before letting the request anywhere near a controller - reject it otherwise. That stops cross-site request forgery: some other, unrelated site tricking your browser into submitting a form to book-reviews on your behalf, using the login session your browser is already holding. Without a token only this app's own pages can generate, that forged request has no way to prove it actually came from here. Every form in this app needs the one line - Breeze's forms already had it, just never explained until now.

BookController@store: saving it

public function store(Request $request)
{
    // No validation yet - $fillable already stops anything other than
    // these columns being mass-assigned, but nothing yet checks that
    // the values themselves make sense. That's next topic's job.
    $book = Book::create($request->all());

    return redirect()->route('books.show', $book);
}

$request->all() is every field the form submitted, as an array - Book::create() accepts it directly because $fillable (from the models topic back in Lesson 1) already filters it down to just the columns Book actually declares safe to mass-assign. That guards against the wrong keys reaching the database - an attacker adding a hidden is_admin field to the form, say - but not against the wrong values: nothing here yet checks that title was actually filled in, or that year is a real year. That's a separate problem from mass assignment, and it's next topic's job.

From a URL to a model, and back again

Topic 2.3 introduced route model binding: {book} in a route pattern resolves straight to a Book $book parameter, because Laravel looks up whatever id is in the URL for you. redirect()->route('books.show', $book) runs that same relationship in reverse. books.show's route pattern is books/{book} - route() needs something to fill that placeholder with, and handing it an actual Book instance, rather than a raw id, is enough: Laravel reads the model's own key (id, by default) and builds /books/21 (or whatever id it turns out to be) automatically.

That id is trustworthy immediately after Book::create() returns, without a second query to look it up - the very same line that runs the INSERT also fills in the auto-incrementing id MySQL just assigned, right there on the $book object handed back. One call creates the row and leaves you holding a model that already knows where to find it.

Trying it out

books/index.blade.php's header gets an "Add Book" link pointing at route('books.create'), so the new form is actually reachable without typing the URL by hand. Fill it in and submit, and the new book's own show page - authors, reviews, all of it - renders exactly like every seeded book, because it's now just another row in the same table.

Leave title blank instead, and the database itself is the only thing standing in the way:

SQLSTATE[23000]: Integrity constraint violation: 1048 Column 'title' cannot be null

That's the NOT NULL constraint from books' own migration, back in Lesson 1, doing exactly what it was built to do - refusing to let a titleless row exist at all. It's also not something any real user should ever see: a raw database exception and a 500 error page, instead of a message next to the field that was actually the problem. Turning that into something worth showing a user is next topic's entire subject.
