Eloquent models and relationships

Book, Author, and Review as Eloquent models - mass assignment, and the belongsToMany/hasMany/belongsTo relationship methods that tie them together.

The four tables from the last topic are just tables so far — nothing in src/ yet turns a row in books into an object you can work with in PHP. That's what this topic adds: a Model class per table (author_book doesn't get one — it's a pivot table, not a thing on its own), plus the relationship methods that let you move between them.

This should look familiar

Your Active Record classes from the prior module already do the two things a model is for: wrap one row as an object, and know how to load and save its own data. If yours looked roughly like this —

class Book {
    public static function find($id) { /* run a SELECT, build a Book */ }
    public function save() { /* run an INSERT or UPDATE */ }
}

$book = Book::find(3);

— an Eloquent model is the same idea, framework-provided:

class Book extends Model {}

$book = Book::find(3);

php artisan make:model Book just generated that second class — an empty body extending Model. Everything else (find, save, create, and more) comes free from the parent class. Eloquent still has to work out which table a Book reads from, and it does that by convention rather than configuration: the class name, lowercased and pluralized — Book → books, Author → authors — matching the table names from the last topic exactly because nothing about them was chosen to be awkward.

Mass assignment: one thing that isn't free

The very first thing worth trying — Book::create(['title' => '...', 'year' => 1999]) — actually fails on a freshly generated model:

Illuminate\Database\Eloquent\MassAssignmentException
Add [title] to fillable property to allow mass assignment on [App\Models\Book].

Eloquent won't let an array of arbitrary keys become column values unless a model explicitly says which attributes that's allowed for — the same instinct behind validating and sanitizing form input by hand in the prior module, just enforced one layer down, at the model itself rather than the form. $fillable is that list:

class Book extends Model
{
    protected $fillable = [
        'title', 'description', 'year', 'image',
        'isbn', 'publisher', 'edition_number', 'price',
    ];

    // relationships below
}

Author and Review each get the same treatment, listing their own columns (Review's includes book_id and user_id — the two foreign keys — since those get set through create() too, not just rating and comment).

The relationships

Six methods, spread across four classes, cover every connection from the domain model: Book::authors() and Author::books() (many-to-many), Book::reviews() and User::reviews() (one-to-many), and Review::book()/Review::user() (the inverse — many reviews to one book or user).

// Book.php
public function authors(): BelongsToMany
{
    return $this->belongsToMany(Author::class);
}

public function reviews(): HasMany
{
    return $this->hasMany(Review::class);
}

belongsToMany is the many-to-many side — it needs a pivot table, and finds author_book the same way models find their own table: by convention, from the two related class names. Nothing here names author_book directly; it didn't have to, because the last topic named that table exactly the way Eloquent expects. hasMany is simpler — it just means "look up rows in reviews whose book_id matches this book." Author::books() and User::reviews() are written the same two ways, just from the other side.

Review::book() and Review::user() are the relationship's inverse — "which one book does this review belong to" rather than "which many reviews does this book have":

// Review.php
public function book(): BelongsTo
{
    return $this->belongsTo(Book::class);
}

belongsTo is what a foreignId column on the model's own table turns into — the mirror image of hasMany, read from the side that actually holds the foreign key.

One piece of magic worth naming

$book->authors() and $book->authors look almost identical, but do different things — this is the one place Eloquent quietly does more than a plain PHP class would. Call it as a method, and you get a query builder back, not results yet — useful when there's more to add before it runs, like $book->authors()->attach($author) to create an author_book row. Access it as a property, with no parentheses, and Eloquent runs the query for you and hands back the actual authors, as a Collection:

$book->authors()->attach($author);      // writes to author_book
$book->authors;                         // reads: a Collection of Author

It's worth seeing the query that property access actually runs, since a many-to-many's SQL isn't obvious from the model code alone the way hasMany's is:

select * from `authors`
inner join `author_book` on `authors`.`id` = `author_book`.`author_id`
where `author_book`.`book_id` = ?

That's exactly the join you'd write by hand from the schema — Eloquent just generates it from belongsToMany() and the tables' own naming conventions, rather than you typing it out every time you need it.

Trying it yourself with tinker

Everything above is worth poking at directly rather than just reading — php artisan tinker, run from the workspace container, drops you into an interactive PHP prompt with the whole app already loaded: every model, the real database connection, all of it, with no route or controller needed just to try something out.

$ php artisan tinker
> $book = \App\Models\Book::create(['title' => 'Dune', 'year' => 1965]);
> $author = \App\Models\Author::create(['name' => 'Frank Herbert']);
> $book->authors()->attach($author);
> $book->authors;
= Illuminate\Database\Eloquent\Collection {
    all: [
      App\Models\Author {
        id: 1,
        name: "Frank Herbert",
        ...
        pivot: Illuminate\Database\Eloquent\Relations\Pivot {
          book_id: 1,
          author_id: 1,
        },
      },
    ],
  }

That last line is the real output — a Collection holding one Author, with a pivot attribute tucked inside it. That's the actual author_book row Eloquent just created and is quietly carrying along, since it's the detail that made this particular Author show up in this particular Book's list. Model classes need their full namespace here (\App\Models\Book, not just Book) — tinker runs outside any file that already has a use statement pulling that name in for you.
