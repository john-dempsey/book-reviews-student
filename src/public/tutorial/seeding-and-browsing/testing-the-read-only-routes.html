Testing the read-only routes

Proving the factories and seeder still behave as documented, then this project's first feature tests - real HTTP requests against books.index/show and authors.index/show, checking the response the way a browser actually would.

Every piece built this lesson - factories, a seeder, two controllers, a handful of Blade views - has only ever been checked by hand: a tinker session, or clicking around the browser after migrate:fresh --seed. Nothing yet fails loudly if a future change quietly breaks one of them. This topic closes that gap, the same way the last lesson's final topic did for the schema - and adds one genuinely new kind of test along the way.

Two more unit tests: proving the factories still work

BookTest, AuthorTest, and ReviewTest already exist from last lesson - each gets one more method, in exactly the same style as the tests already there, just building its row through a factory instead of typing every attribute by hand:

public function test_the_factory_creates_a_valid_book(): void
{
    $book = Book::factory()->create();

    $this->assertDatabaseHas('books', ['id' => $book->id]);
    $this->assertNotEmpty($book->title);
    $this->assertGreaterThanOrEqual(1950, $book->year);
}

Nothing here is a new testing idea - assertDatabaseHas() and plain PHPUnit assertions are both already familiar. What's worth checking is different: not "does this exact value end up in the database" (the factory's values are random), but "is whatever the factory produced actually plausible" - a real title, a year inside the range BookFactory promises. ReviewTest gets the same treatment for rating:

public function test_the_factory_creates_a_review_with_a_rating_between_one_and_five(): void
{
    $review = Review::factory()->create();

    $this->assertGreaterThanOrEqual(1, $review->rating);
    $this->assertLessThanOrEqual(5, $review->rating);
}

Testing the seeder

Last topic's "checking the result" section ran a handful of tinker commands by hand after seeding - counting users, authors, books, reviews, and confirming the two co-written books and two unreviewed ones actually turned up. A test can run that exact check automatically:

class DatabaseSeederTest extends TestCase
{
    use RefreshDatabase;

    public function test_seeding_produces_the_expected_catalogue_shape(): void
    {
        $this->seed();

        $this->assertSame(5, User::count());
        $this->assertSame(5, Author::count());
        $this->assertSame(20, Book::count());
        $this->assertSame(60, Review::count());
    }
}

$this->seed() is new - it runs DatabaseSeeder (and everything it calls) inside the test's own transaction, the same one-shot job php artisan migrate:fresh --seed does from the terminal, just repeatable as an assertion instead of something you eyeball once. Two more methods in the same class check the less obvious guarantees from last topic's fixed review-count array:

public function test_seeding_produces_two_co_written_books(): void
{
    $this->seed();

    $this->assertSame(2, Book::has('authors', '>=', 2)->count());
}

public function test_seeding_leaves_two_books_without_reviews(): void
{
    $this->seed();

    $this->assertSame(2, Book::doesntHave('reviews')->count());
}

Both read directly as the same queries typed into tinker last topic - now checked on every test run, not just the one time someone happened to look.

Feature tests: testing the actual browsing experience

Every test so far - this lesson and last - has been a unit test: building rows and calling methods directly, no HTTP involved. BookController and AuthorController are the first code in this course worth a feature test instead - one that makes a real request against a route and checks the response, closer to how a browser would actually use the app.

class BookTest extends TestCase
{
    use RefreshDatabase;

    public function test_guests_are_redirected_to_login(): void
    {
        $response = $this->get(route('books.index'));

        $response->assertRedirect(route('login', absolute: false));
    }
}

$this->get() sends a real GET request through the whole framework - routing, middleware, the controller, the view - and returns a TestResponse to make assertions against. route('books.index') builds the URL from the route's name, the same way a Blade view would, rather than hardcoding /books. Since books.index sits behind the auth middleware, an unauthenticated request never reaches BookController at all - it's redirected to route('login') first, and assertRedirect() checks exactly that.

Logged in, the index page actually shows a book:

public function test_the_index_page_lists_books(): void
{
    $user = User::factory()->create();
    Book::factory()->create(['title' => 'Dune']);

    $response = $this->actingAs($user)->get(route('books.index'));

    $response->assertOk();
    $response->assertSee('Dune');
}

actingAs($user) is what a login form and a session cookie do together in a real browser, collapsed into one call - every request made after it is authenticated as that user. assertSee() searches the actual rendered HTML for the given text; here, that a book titled "Dune" made it all the way from a factory call, through BookController@index, through books/partials/card.blade.php, into the response.

The show page displays what it's supposed to:

public function test_the_show_page_displays_a_books_authors_and_reviews(): void
{
    $user = User::factory()->create();
    $book = Book::factory()->create(['title' => 'Dune']);
    $book->authors()->attach(Author::factory()->create(['name' => 'Frank Herbert']));
    Review::factory()->create([
        'book_id' => $book->id,
        'user_id' => $user->id,
        'comment' => 'A genuine classic.',
    ]);

    $response = $this->actingAs($user)->get(route('books.show', $book));

    $response->assertOk();
    $response->assertSee('Frank Herbert');
    $response->assertSee('A genuine classic.');
}

This is the test this topic's title actually promises: proof that books.show really does display a book's authors and reviews, not just that it returns a 200. route('books.show', $book) passes the model straight in - the same route model binding from the last topic, now building a URL instead of resolving one.

A route that binds a model can also fail to find one:

public function test_a_nonexistent_book_returns_a_404(): void
{
    $user = User::factory()->create();

    $response = $this->actingAs($user)->get('/books/999');

    $response->assertNotFound();
}

Route model binding looks up a Book with id 999, finds nothing, and Laravel turns that failed lookup into a 404 automatically - no code in BookController@show handles this case explicitly, because none needs to.

tests/Feature/AuthorTest.php mirrors all four of these exactly, one level of the domain down - the same guest redirect, an index page that lists a seeded author, a show page proving authors.show displays that author's books, and a 404 for an id that doesn't exist.

Running everything

Tests:    49 passed (105 assertions)

Every test written across this lesson - the new factory checks, the seeder test, and both feature test files - passes alongside everything carried over from Lesson 1, one combined suite proving the whole catalogue actually holds together: seeded correctly, and browsable by anyone logged in.

What's still missing

The catalogue can be browsed, and now provably so - but it still can't be changed. There's no way to add a book, fix a typo in one, or remove it once it's there. Lesson 3 picks up from here with the rest of BookController - create, store, edit, update, and destroy.
