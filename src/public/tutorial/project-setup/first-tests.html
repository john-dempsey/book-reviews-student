First tests: models

PHPUnit basics, how Laravel keeps tests from touching real data, and the first real tests against Book, Author, and Review.

The last topic's closing section promised this moment: an actual schema, actual models, actual relationships — finally something worth testing. This topic covers PHPUnit itself (you haven't used it before), how Laravel keeps a test from quietly corrupting real data, and this project's first real tests.

What PHPUnit actually is

PHPUnit is the testing framework Laravel ships with by default. A test is just a method, on a class extending Tests\TestCase, whose name starts with test_:

class BookTest extends TestCase
{
    public function test_a_book_can_be_created(): void
    {
        // ...
    }
}

Inside that method, you do something, then assert what should be true afterward — assertTrue(), assertCount(), and Laravel's own database-aware assertions like assertDatabaseHas(), which you'll see below. php artisan test — already familiar from running the suite after every topic so far — is what actually runs every method like this one, in every file under tests/, and reports which passed.

The database problem, and how it's solved here

A test that creates a Book has to hit a real database to do it — so what stops ten new test runs a day from filling book_reviews with junk titled "Test Book"? Three real options exist:

  1. Point tests at a separate, disposable database — its own name, its own connection settings, wiped and rebuilt as often as you like, completely independent of the data you're actually browsing in phpMyAdmin.
  2. Run tests against an in-memory SQLite database instead of MySQL — this is actually what a fresh laravel new project is configured to do out of the box. Fast, and automatically thrown away, but a genuinely different database engine from the one this app actually runs on — not a risk for every test, but the kind of gap that can let a MySQL-specific detail go untested.
  3. Run tests against the exact same database the app uses, relying on something else to stop any of it from sticking.

This project uses option 3 — the same book_reviews MySQL database your own browsing uses — via a trait called RefreshDatabase:

class BookTest extends TestCase
{
    use RefreshDatabase;

    // ...
}

RefreshDatabase wraps each test method in a database transaction, and rolls that transaction back the moment the test method ends. Every Book::create() inside a test really does run a real INSERT, against the real database — the assertions in that same test genuinely see it. It just never commits. Proof, from a real test run: a test creating one Book and asserting assertDatabaseCount('books', 1) — which passes — followed immediately by querying book_reviews directly, outside the test, for the same count:

books_in_real_db
0

Whatever ran inside the test is simply gone once it ends, like it never happened — which is exactly the property you want.

Writing the first tests

tests/Unit/BookTest.php, AuthorTest.php, and ReviewTest.php cover the three models from the last topic, one file each — following the same tests/Unit/ vs. tests/Feature/ split mentioned back when the tests/ folder was still empty. Each test builds its own rows directly (Book::create([...]), User::create([...])) rather than through a factory — there still isn't one yet; that's Lesson 2.

A model can actually be created:

public function test_a_book_can_be_created(): void
{
    $book = Book::create([
        'title' => 'The Pragmatic Programmer',
        'year' => 1999,
    ]);

    $this->assertDatabaseHas('books', ['title' => 'The Pragmatic Programmer']);
    $this->assertSame(1999, $book->year);
}

assertDatabaseHas() is Laravel's own assertion, on top of PHPUnit's — it runs a real query and fails if no row matches. Reading it as SQL, it's asserting exactly SELECT * FROM books WHERE title = '...' found something.

A relationship actually resolves:

public function test_a_book_has_many_authors(): void
{
    $book = Book::create(['title' => 'Clean Code', 'year' => 2008]);
    $author = Author::create(['name' => 'Robert C. Martin']);

    $book->authors()->attach($author);

    $this->assertCount(1, $book->authors);
    $this->assertTrue($book->authors->first()->is($author));
}

->is($author) is Eloquent's way of asking "is this literally the same row" — comparing two model instances by class and primary key, rather than comparing every attribute by hand.

A business rule actually holds, not just the schema's shape — this is the one test expecting a failure, deliberately:

public function test_a_user_cannot_review_the_same_book_twice(): void
{
    $book = $this->makeBook();
    $user = $this->makeUser();

    Review::create(['book_id' => $book->id, 'user_id' => $user->id, 'rating' => 5]);

    $this->expectException(UniqueConstraintViolationException::class);

    Review::create(['book_id' => $book->id, 'user_id' => $user->id, 'rating' => 1]);
}

expectException() tells PHPUnit, before the risky line runs, exactly which exception the next line should throw — the test only passes if that second create() actually fails, proving the unique index from the migrations topic is really being enforced by the database, not just assumed to be there.

Between the three files, every relationship from the last topic gets exercised at least once, in both directions: Book::authors() / Author::books(), Book::reviews() / User::reviews(), and Review::book() / Review::user().

Running them

Nothing new here — php artisan test, same as every topic so far, now reports real coverage instead of just Breeze's own generated tests:

PASS  Tests\Unit\AuthorTest
✓ an author can be created
✓ an author has many books

PASS  Tests\Unit\BookTest
✓ a book can be created
✓ a book has many authors
✓ a book has many reviews

PASS  Tests\Unit\ReviewTest
✓ a review can be created
✓ a review belongs to a book
✓ a review belongs to a user
✓ a user can have many reviews
✓ a user cannot review the same book twice

--filter=BookTest narrows a run to one class, or one test, by name — worth knowing once a suite has grown past a handful of files, rather than re-running everything for a one-line change.
