Reading the catalogue: index and show

BookController and AuthorController's read-only index/show actions, wired to real routes with route model binding - then the Blade layout, partials, and loops that turn seeded rows into an actual catalogue you can click through.

The catalogue built last topic is real, but it only exists in the database - no page lists the books, no page shows one book's authors and reviews. Getting from a seeded table to something you can click through touches every layer of the app at once: a route to match the URL, a controller to fetch the right rows, and a Blade view to turn them into HTML. This topic builds all three, for two resources at once - Book and Author.

Routing to a controller

Every route so far in this app has been either a closure (Route::get('/', function () { ... })) or one of Breeze's own already-generated auth routes. BookController and AuthorController are the first controllers this course writes, so they need routes of their own.

A resource - in the CRUD sense - conventionally needs up to seven routes: list them all (index), show a form to create one (create), handle that form's submission (store), show one (show), show a form to edit one (edit), handle that form's submission (update), and delete one (destroy). Rather than writing seven Route::get/Route::post/... lines by hand, Route::resource() registers all seven in one line, wired to seven conventionally-named controller methods:

Route::resource('books', BookController::class);

BookController doesn't have all seven methods yet - only index and show exist so far; creating, editing, and deleting a book properly (with validation) is a later lesson's job. ->only() restricts the generated routes to just the ones that actually exist right now:

Route::resource('books', BookController::class)->only(['index', 'show']);
Route::resource('authors', AuthorController::class)->only(['index', 'show']);

That one line each registers:

GET|HEAD   books ............ books.index › BookController@index
GET|HEAD   books/{book} ..... books.show › BookController@show

(php artisan route:list --path=books prints exactly that.) The names on the left - books.index, books.show - are what route('books.show', $book) in a Blade view refers to; naming a route rather than writing /books/1 directly means the actual URL can change later without breaking every link to it.

{book} and route model binding

books/{book} looks like it hands BookController@show a raw id - but the method signature is:

public function show(Book $book)
{
    // ...
}

Laravel matches the {book} segment in the route to the $book parameter's name, looks up that id, and injects the actual Book model - no Book::findOrFail($id) needed. Visit /books/999 for an id that doesn't exist, and Laravel returns a 404 before show() even runs. This is route model binding, and it's why every method below takes a model instance directly instead of an id.

Still behind the login wall

Both resource routes are registered inside the same Route::middleware('auth')->group() that already protects /profile - browsing the catalogue needs a logged-in user too, the same as everything else in this app past the welcome page. Nothing about index/show themselves requires that; it's a deliberate consistency choice for this app, not a limitation of resource routes in general.

The first controllers you've written yourself

Breeze generated Auth/AuthenticatedSessionController and ProfileController when it installed authentication - useful, but you never had to write a line of either. BookController and AuthorController are the first controllers in this course you create and fill in, the same way:

php artisan make:controller BookController

That generates an empty class extending the same Controller base every Breeze controller already extends. Nothing forces the method names inside it - but Route::resource() above only works because index and show are named exactly what a resource controller is expected to call them.

BookController@index: listing, with paginate()

public function index()
{
    $books = Book::with('authors')
        ->withCount('reviews')
        ->withAvg('reviews', 'rating')
        ->orderBy('title')
        ->paginate(12);

    return view('books.index', compact('books'));
}

paginate(12) is new: instead of one collection holding every book, it returns 12 at a time and gives the view everything it needs to render "next page"/"previous page" links, reading the current page straight from the URL's own ?page= query string. get() or all() would run too, but would hand the view every seeded book on one page.

with('authors') loads every matching book's authors in one extra query, up front. The alternative - letting each book load its own $book->authors the first time a Blade view actually touches it - is the classic N+1 problem: one query for the books, then one more per book just to find out who wrote it. Twelve books on a page would mean thirteen queries instead of two. withCount('reviews') and withAvg('reviews', 'rating') solve the same problem for numbers the view needs but not the rows behind them: each adds one extra column (reviews_count, reviews_avg_rating) to the same query, computed by the database, instead of loading every review just to call ->count() or ->avg('rating') in PHP.

BookController@show: load() instead of with()

public function show(Book $book)
{
    $book->load(['authors', 'reviews.user']);

    return view('books.show', compact('book'));
}

Route model binding has already fetched $book by the time show() runs, so there's no query left to attach with() to - load() is the equivalent for a model that already exists, adding relationships to it after the fact. 'reviews.user' is dot notation for a nested relationship: load every review, and for each of those, load the user who wrote it - one query for the reviews, one more for all their users at once, still not one query per review.

AuthorController: the same shape, one level down

public function index()
{
    $authors = Author::withCount('books')
        ->orderBy('name')
        ->paginate(12);

    return view('authors.index', compact('authors'));
}

public function show(Author $author)
{
    $author->load(['books' => function ($query) {
        $query->with('authors')->withCount('reviews')->withAvg('reviews', 'rating');
    }]);

    return view('authors.show', compact('author'));
}

show()'s books need their own authors, review count, and average rating loaded too - because the author's page reuses the exact same book card partial the /books listing uses (more on that below). Passing a closure to load() adds with()/withCount()/withAvg() constraints onto a relationship as it's loaded, rather than just naming it.

From <x-app-layout> to one card

Every page so far - dashboard.blade.php, the auth screens - starts the same way:

<x-app-layout>
    <x-slot name="header">
        <h2>...</h2>
    </x-slot>

    <!-- page content -->
</x-app-layout>

<x-app-layout> is a Blade component - a reusable chunk of markup invoked like an HTML tag. It isn't a Blade file directly; it's App\View\Components\AppLayout, a small PHP class whose only job is to say which view actually renders:

class AppLayout extends Component
{
    public function render(): View
    {
        return view('layouts.app');
    }
}

resources/views/layouts/app.blade.php is that view - the shared HTML document (<html>, <head>, Tailwind's @vite tags, <body>) every page in the app renders inside of. Two things make it reusable rather than one static page: {{ $slot }}, where whatever sits between the <x-app-layout> tags ends up; and the named <x-slot name="header">, for the one part (the page title bar) that isn't just "everything inside the tags" - @isset($header) in the layout means a page that never defines one just doesn't get that bar at all.

layouts/app.blade.php also does @include('layouts.navigation'). That's a partial - a plain Blade file included as-is wherever @include is written, sharing whatever variables are already in scope. Unlike a component, a partial has no class of its own, no slots, and no declared list of what it expects - closer to the file's contents being pasted in place. layouts/navigation.blade.php is where the new "Books" and "Authors" links actually live, each using request()->routeIs('books.*') to decide whether it should render as the active one - true for books.index and books.show alike, since * matches anything after books..

One index page, start to finish

authors/index.blade.php uses almost everything above in one page:

<x-app-layout>
    <x-slot name="header">
        <h2 class="...">{{ __('Authors') }}</h2>
    </x-slot>

    <div class="grid grid-cols-1 sm:grid-cols-2 gap-6">
        @forelse ($authors as $author)
            @include('authors.partials.card', ['author' => $author])
        @empty
            <p class="text-gray-600 col-span-full">No authors in the catalogue yet.</p>
        @endforelse
    </div>

    {{ $authors->links() }}
</x-app-layout>

@forelse ... @empty ... @endforelse is @foreach with a built-in "what if the collection is empty" branch, in one directive instead of a @foreach wrapped in an @if ($authors->count()). @include('authors.partials.card', [...]) renders authors/partials/card.blade.php once per author, passing that one author in as $author - the same @include mechanism as the navigation partial above, just called once per loop iteration instead of once per page. {{ $authors->links() }} is what paginate() in the controller was for - Laravel's own default pagination view, rendering the actual "1 2 3 ... Next" links.

A partial reused across two different pages

books/partials/card.blade.php isn't only used by /books:

<div class="bg-white overflow-hidden shadow-sm rounded-lg flex flex-col">
    <img src="{{ $book->image ?? asset('images/book-placeholder.png') }}"
         alt="Cover of {{ $book->title }}"
         class="w-full h-48 object-contain">

    <div class="p-4 flex flex-col grow">
        <h3 class="font-semibold text-lg text-gray-900">
            <a href="{{ route('books.show', $book) }}">{{ $book->title }}</a>
        </h3>

        <p class="text-sm text-gray-600 mt-1">
            {{ $book->authors->pluck('name')->join(', ') ?: 'Unknown author' }}
            &middot; {{ $book->year }}
        </p>

        <p class="text-sm text-gray-500 mt-auto pt-2">
            @if ($book->reviews_count > 0)
                {{ number_format($book->reviews_avg_rating, 1) }} / 5
                ({{ $book->reviews_count }} {{ Str::plural('review', $book->reviews_count) }})
            @else
                No reviews yet
            @endif
        </p>
    </div>
</div>

authors/show.blade.php loops over an author's own books through this exact same partial:

@forelse ($author->books as $book)
    @include('books.partials.card', ['book' => $book])
@empty
    <p class="text-gray-600 col-span-full">No books by this author yet.</p>
@endforelse

One partial, two different pages - which is exactly why AuthorController@show bothers loading each book's own authors and review stats above: the partial expects the same shape of $book regardless of which page included it. $book->authors->pluck('name')->join(', ') turns the loaded authors collection into "Name One, Name Two" in one line; Str::plural('review', $book->reviews_count) is a small helper that returns "review" or "reviews" depending on the count it's given, rather than a @if ($count === 1) for one word.

Displaying a book's reviews

books/show.blade.php loops over $book->reviews the same way, through its own partial:

@forelse ($book->reviews as $review)
    @include('reviews.partials.review', ['review' => $review])
@empty
    <p class="text-gray-600">No reviews yet.</p>
@endforelse

reviews/partials/review.blade.php itself is small - a reviewer's name, their rating, an optional comment, and the date:

<div class="border-b border-gray-200 py-4 last:border-b-0">
    <div class="flex items-center justify-between">
        <span class="font-medium text-gray-900">{{ $review->user->name }}</span>
        <span class="text-sm text-gray-500">{{ $review->rating }} / 5</span>
    </div>

    @if ($review->comment)
        <p class="text-gray-700 mt-1">{{ $review->comment }}</p>
    @endif

    <p class="text-xs text-gray-400 mt-1">{{ $review->created_at->format('d M Y') }}</p>
</div>

@if ($review->comment) matters because comment is nullable - some reviews are just a star rating. $review->user->name only avoids a second query per review because BookController@show already loaded 'reviews.user' above - without that, this one line would be the N+1 problem happening in the view instead of the controller.

Placeholder images

Book covers and author photos are both nullable columns, and nothing populates them yet - BookFactory and AuthorFactory leave image as null on purpose. Uploading a real image is a later lesson's job, once a form exists to attach a file to a book at all; for now, every card and show page falls back to a static placeholder instead of a broken image:

<img src="{{ $book->image ?? asset('images/book-placeholder.png') }}" ...>

The two placeholder graphics live at public/images/book-placeholder.png and public/images/author-placeholder.png - public/ is the same folder the first lesson pointed out as "anything Apache serves directly," the same reason favicon.ico or this tutorial site itself work without going through a route at all. asset() builds the full URL to a file under public/ (http://.../images/book-placeholder.png), the same way route() builds a URL from a route's name rather than a raw path.

What's still missing

Every book and author can be browsed now, but only by someone already logged in, and only ever read - there's still no way to add a book, edit one, or leave a review. Proving these new routes actually work, with real tests instead of clicking through the browser by hand, is next.
