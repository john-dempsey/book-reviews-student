Handoff: what Part 2 will add

What six weeks of Book Reviews actually built, and a scoped, deliberate exception to this course's own no-forward-references rule: a preview of the role-based authorization Part 2 picks up from here.

Every topic so far has stuck to one rule without exception: nothing gets used before it's been taught. This one breaks it, on purpose, for one paragraph at a time - previewing two things a different instructor builds on top of this app in the six weeks after this one. It's flagged here, explicitly, because that rule matters everywhere else in this course; this closing topic is the one deliberate, bounded exception to it, not a crack in it.

What exists

A logged-in user can browse a catalogue of books - searchable by title, author, or year - see each book's authors and existing reviews, and leave exactly one review per book, with a rating and an optional comment. They can edit or delete their own reviews from a dedicated "My Reviews" page, but nobody else's. Authors have their own browsable list, each showing the books attributed to them. Every one of those routes sits behind Breeze's real session-based login, not a stub. All of it is backed by 83 tests, and every read page runs a flat number of database queries regardless of how much data sits behind it - proven, not assumed. That's the whole of Part 1: a real, working, fully tested book review catalogue, with nothing missing from what it claims to do.

What it deliberately doesn't do yet is anything role-based. Every registered user has exactly the same permissions as every other one - there's no "admin" who can edit someone else's book, no moderator who can remove someone else's review. That gap was named on purpose, all the way back in this course's very first lesson, as a boundary for what six weeks could reasonably cover - not a gap anyone was meant to quietly work around. This is where it picks back up.

Role-based authorization: users.role

Nothing in this app currently reads a role, so nothing in its schema declares one - a column with no code path exercising it would just be a forward reference sitting in the database with nothing pointing at it yet. Part 2 adds it the same way every other column in this app arrived: its own migration, added when it's actually needed, not stubbed out early "to save a step." Once it exists, it's what everything below actually checks.

Policies: the framework's real answer to the Lesson 4 stand-in

ReviewController currently guards edit(), update(), and destroy() with a private method:

private function authorizeOwner(Review $review): void
{
    if ($review->user_id !== auth()->id()) {
        abort(403);
    }
}

That was flagged as a stand-in the day it was written - a plain, honest guard clause standing in for a Policy, Laravel's actual dedicated mechanism for "can this user do this to this model?" A Policy is a class the framework already knows how to find - php artisan make:policy ReviewPolicy --model=Review generates one wired to Review by naming convention alone - with one method per action:

class ReviewPolicy
{
    public function update(User $user, Review $review): bool
    {
        return $user->id === $review->user_id;
    }
}

Once that exists, the controller stops checking ownership itself and just asks:

public function update(Request $request, Review $review)
{
    $this->authorize('update', $review);
    // ...
}

Read that as a sketch, not a build - this app's own authorizeOwner() is untouched, still doing exactly what it's always done. But the two methods above say the same thing: "only the review's own author may update it." authorizeOwner() said it as a hand-written if. A Policy says it as a class Laravel calls for you, the same relationship Eloquent models have to hand-written SQL, or $request->validate() has to a hand-written validator class - a familiar shape, a framework provided version. Once users.role exists too, the same Policy method is exactly where a role check would go: $user->role === 'admin' || $user->id === $review->user_id, one extra condition, the same method, the same pattern - a moderator allowed to remove anyone's review without Book Reviews' access-control logic scattering itself back out across controllers to get there.

A lower-priority extension point: editions

One more deliberate simplification is worth naming, though it's a smaller thing to pick up than authorization and nothing about it is expected to happen soon: books currently carries isbn, publisher, price, and edition_number directly on itself, so every book has exactly one implicit edition. A real catalogue might let one book have many editions - different printings, different ISBNs, different prices

  • as a proper one-to-many relationship instead. Nothing about the data those four columns hold would be lost splitting them back out; it's a clean, well-understood extension point if it's ever worth the extra model, migration, and pair of controllers it would take - not a bug being carried forward.

Part 1 complete

Six lessons: a schema and Eloquent models with real authentication in Lesson 1, seeded demo data and read-only browsing in Lesson 2, full CRUD for the book catalogue in Lesson 3, reviews with an ownership check in Lesson 4, search across title, author, and year in Lesson 5, and this closing pass confirming the query performance and test coverage both hold up under real scrutiny. What started as a bare laravel new . install is now a working application with nothing hidden behind it - every route tested, every page's query count measured and proven flat, and exactly two things - a role, and the Policy that reads it - left for the next six weeks to build.
