My reviews

A /my-reviews page listing everything the logged-in user has written, across every book - a plain route rather than a resource action, auth()->user()->reviews() reused the same way books.index already reuses withCount/withAvg, and latest() as a small new shorthand.

Every review so far has only ever been seen in the context of the book it's about - written from a book's page, edited and deleted from a link sitting right next to it on that same page. There's still no way to answer a simpler question: what have I actually written, across every book I've reviewed? This topic adds exactly that - one page, listing every review the logged-in user has ever left.

A route that isn't one of the seven

Every route this app has added so far has been part of a Route::resource() call - index, create, store, show, edit, update, destroy, always some subset of the same seven names. This page doesn't fit any of them. It isn't reviews.index, because a global listing of every review ever written isn't a page this app has - reviews are always shown in the context of a book (books.show) or, from this topic on, in the context of a user. Trying to force it into index would mean teaching a lie: that this page lists "the reviews resource," when it actually lists one particular relationship for one particular person. So it gets a plain route instead, the same way /dashboard already does:

Route::get('/my-reviews', [ReviewController::class, 'mine'])->name('reviews.mine');

reviews.mine still lives under the reviews. naming umbrella, the same namespacing reviews.edit/reviews.update/reviews.destroy already use, even though it isn't one of Route::resource()'s generated names - nothing about route naming requires the seven resource names, they're just the ones Route::resource() happens to generate automatically.

ReviewController@mine: whose reviews, and how many

public function mine()
{
    $reviews = auth()->user()->reviews()
        ->with('book')
        ->latest()
        ->paginate(12);

    return view('reviews.mine', compact('reviews'));
}

auth()->user()->reviews() calls the HasMany relationship User::reviews() already defined - the same relationship $book->reviews() has used from a Book's side since Lesson 1, just walked from the other end. Calling it with () (rather than the property access auth()->user()->reviews, which would run the query and return every row at once) is what makes it a query builder that ->with(), ->latest(), and ->paginate() can still be chained onto - exactly the same builder-vs-already-loaded distinction books.index relies on when it calls Book::with('authors') instead of loading a Book first and asking about its authors after.

->with('book') eager-loads each review's book in the same one extra query books.show's own $book->load(['authors', 'reviews.user']) already uses to avoid running a fresh query per row - this page prints every review's book title, so without it there'd be one query per review instead of one query total. ->paginate(12) is the exact same call books.index already makes, same page size and everything - a user with more written reviews than fit on one page gets the same {{ $reviews->links() }} footer books.index already renders, for free.

->latest() is new, though small: it's shorthand for orderByDesc('created_at') - Eloquent's own name for "the normal way to sort things by recency." Every listing so far (books.index, authors.index) has sorted by name instead, because a catalogue is naturally alphabetical; a list of your own reviews reads more naturally most-recent-first, so this is the first place recency order actually fits better.

The view: one card per review, this time with the book's name on it

reviews/partials/review.blade.php already exists - the partial books/show.blade.php loops over to print each review on a book's page. It leads with $review->user->name, because on a book's page the interesting question is who wrote each review; the book itself is already the whole page. Here it's the reverse - every review belongs to the same person, so printing that person's own name back at them on every row would be pointless. What's actually useful here is which book each review is about, so this gets its own small partial rather than reusing that one:

<div class="border-b border-gray-200 py-4 last:border-b-0">
    <div class="flex items-center justify-between">
        <a href="{{ route('books.show', $review->book) }}" class="font-medium text-gray-900 hover:underline">
            {{ $review->book->title }}
        </a>
        <span class="text-sm text-gray-500">{{ $review->rating }} / 5</span>
    </div>

    @if ($review->comment)
        <p class="text-gray-700 mt-1">{{ $review->comment }}</p>
    @endif

    <div class="flex items-center justify-between mt-1">
        <p class="text-xs text-gray-400">{{ $review->created_at->format('d M Y') }}</p>

        <div class="flex items-center gap-3">
            <a href="{{ route('reviews.edit', $review) }}" class="text-xs text-gray-500 hover:text-gray-800 hover:underline">
                {{ __('Edit') }}
            </a>

            <form method="POST" action="{{ route('reviews.destroy', $review) }}"
                  onsubmit="return confirm('Delete this review? This cannot be undone.');">
                @csrf
                @method('DELETE')
                <button type="submit" class="text-xs text-red-600 hover:text-red-800 hover:underline">
                    {{ __('Delete') }}
                </button>
            </form>
        </div>
    </div>
</div>

Notice what's missing compared to the book-page version: no @if ($review->user_id === auth()->id()) around the Edit/Delete controls. On a book's page, most reviews belong to someone else, so that check decides whether to show the controls at all. Every review reviews.mine ever lists belongs to the person viewing the page - the query itself, auth()->user()->reviews(), already guarantees that - so there's nothing left to check before showing them. The links point at the exact same reviews.edit/reviews.destroy routes either way, still guarded server-side by authorizeOwner() regardless of which page linked to them.

reviews/mine.blade.php wraps that partial the same way books/index.blade.php wraps books/partials/card.blade.php - a @forelse, an @empty branch for a user who hasn't reviewed anything yet, and the same {{ $reviews->links() }} footer:

<x-app-layout>
    <x-slot name="header">
        <h2 class="font-semibold text-xl text-gray-800 leading-tight">
            {{ __('My Reviews') }}
        </h2>
    </x-slot>

    <div class="py-12">
        <div class="max-w-4xl mx-auto sm:px-6 lg:px-8">
            <div class="bg-white overflow-hidden shadow-sm rounded-lg p-6">
                @forelse ($reviews as $review)
                    @include('reviews.partials.mine-row', ['review' => $review])
                @empty
                    <p class="text-gray-600">
                        {{ __("You haven't reviewed any books yet.") }}
                        <a href="{{ route('books.index') }}" class="text-gray-800 underline">{{ __('Browse the catalogue') }}</a>
                        {{ __('to find one.') }}
                    </p>
                @endforelse
            </div>

            <div class="mt-6">
                {{ $reviews->links() }}
            </div>
        </div>
    </div>
</x-app-layout>

One more link in the navigation

Books and Authors have had their own link in the top navigation bar since Lesson 2. "My Reviews" joins them - in both the desktop menu and its collapsed mobile equivalent - pointing at the new named route:

<x-nav-link :href="route('reviews.mine')" :active="request()->routeIs('reviews.mine')">
    {{ __('My Reviews') }}
</x-nav-link>

Trying it out

Log in and click "My Reviews" in the navigation bar, and every review written by that account shows up, most recent first, each one linking back to its own book - fifteen written reviews means a second page, reached through the same pagination links books.index already taught. Click a book's title from this page and it lands on books.show, the same page the review was originally written from. Edit or delete a review from here, and it behaves exactly as it did from the book's own page, because it's the exact same route either way - this page is just a second way of reaching it.

Log in as a brand-new account that hasn't reviewed anything yet, and the page shows a plain message instead of an empty list, with a link back to the catalogue to go find something to review.

Between all three review topics, the app now has the complete other half of "book reviews": write one, fix or retract it, and see every one you've written in one place - all of it guarded so that only the person who wrote a review can ever change or remove it. What hasn't been checked yet is that the ownership guard actually holds up under a real, automated test rather than manual curl requests - that's the next and final topic of this lesson.
