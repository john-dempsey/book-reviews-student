Writing a review

ReviewController@create and @store behind this course's first nested resource route, rating/comment validation, and turning the migration's unique index into a friendly redirect instead of a raw duplicate-entry error.

The catalogue itself is finished - a book can be added, edited, and removed, each step validated. Nothing has actually let anyone leave a review yet, though - every review on a book's page so far arrived through a seeder, the same way every book once did before Lesson 3. This topic adds the first way to change that: a form for reviewing a book, and the controller code that saves what it submits.

A route nested under its book

Every route so far - books, authors - has stood on its own. A review never makes sense without a book to belong to, and this is the first route in the app that says so directly:

Route::resource('books.reviews', ReviewController::class)->only(['create', 'store']);

Route::resource('books.reviews', ...) is Route::resource('books', ...) with one more segment - books.reviews reads as "reviews, nested under books." It generates GET /books/{book}/reviews/create, named books.reviews.create, and POST /books/{book}/reviews, named books.reviews.store - the URL itself carries which book a review is being written for, rather than a review needing its own standalone /reviews/create with a hidden book-picker field. ->only(['create', 'store']) is exactly the familiar restriction from every resource route in this app so far - editing and deleting a review are a later topic's job, not this one's.

ReviewController@create: showing the form

public function create(Book $book)
{
    return view('reviews.create', compact('book'));
}

Route model binding does the same job it always has, just reading {book} out of a longer URL than usual - books/{book}/reviews/create still resolves straight to a Book $book parameter, no lookup written by hand. The view needs that book both to know which one it's reviewing and to build the form's own submit URL.

The form: a <select>, and @selected

rating is naturally a small, fixed set of choices rather than free text - a dropdown fits better here than the text inputs every form so far has used:

<select id="rating" name="rating" class="mt-1 block w-full border-gray-300 focus:border-indigo-500 focus:ring-indigo-500 rounded-md shadow-sm" required>
    <option value="">{{ __('Select a rating') }}</option>
    @for ($i = 1; $i <= 5; $i++)
        <option value="{{ $i }}" @selected(old('rating') == $i)>{{ $i }} / 5</option>
    @endfor
</select>
<x-input-error :messages="$errors->get('rating')" class="mt-2" />

@for builds the five options the same way a plain PHP for loop would. @selected(...) is new, but small: it prints the selected attribute when its condition is true, and prints nothing at all when it's false - @selected(old('rating') == $i) is the exact same old()-driven repopulation idea from topic 3.2, just applied to a <select> instead of a text input's value="". comment needs nothing new at all - the same <textarea> and old() pattern topic 3.3 already used for a book's description.

ReviewController@store: the two things worth checking

public function store(Request $request, Book $book)
{
    $validated = $request->validate([
        'rating' => 'required|integer|between:1,5',
        'comment' => 'nullable|string',
    ]);

Nothing here is new - required, nullable, integer have all appeared already; between:1,5 is the same bounding idea as max:255, just checking both ends of a range instead of one. A failure behaves exactly as it has since topic 3.2: redirected straight back to the form, with a message under rating and whatever was already typed still there.

One review per person per book

A rating and a comment aren't the only thing worth checking. Back in Lesson 1, the reviews migration added a unique index on [book_id, user_id] - the database itself already refuses a second row for the same pair. Leave the check out of the controller entirely, and reviewing a book twice looks like this instead:

SQLSTATE[23000]: Integrity constraint violation: 1062 Duplicate entry
'82-56' for key 'reviews.reviews_book_id_user_id_unique'

The same shape of problem topic 3.1 hit with a blank title - a real constraint doing exactly its job, and a raw database exception the wrong way for any user to find that out. The fix here isn't $request->validate() again, though - nothing about what was typed into the form was wrong, so there's no rule string that catches it. This is a check against the rest of the database, not against the request:

    // The migration's unique index already stops a second row for this
    // exact pair existing - this check exists so trying anyway gets the
    // same friendly redirect-back-with-errors treatment as any other
    // validation failure, rather than the raw exception above reaching
    // the browser.
    if ($book->reviews()->where('user_id', auth()->id())->exists()) {
        return back()->withErrors([
            'rating' => 'You have already reviewed this book.',
        ])->withInput();
    }

    $validated['user_id'] = auth()->id();
    $book->reviews()->create($validated);

    return redirect()->route('books.show', $book);
}

$book->reviews()->where('user_id', auth()->id())->exists() asks the same question the unique index enforces, just before the INSERT happens instead of after: does a review from this user already exist on this book? back()->withErrors([...])->withInput() is the exact same shape validate()'s own automatic failure builds - a real message, attached to a real field, on a redirect back to the form - written out by hand this one time because the thing that failed isn't a rule validate() knows how to check on its own. auth()->id() is new here, though the idea isn't: every form so far has trusted values the request carried in; which user is submitting isn't one of them - trusting a hidden user_id field would let anyone claim to be anyone. auth()->id() reads it from the actual logged-in session instead, the same session actingAs() and Breeze's login have relied on all along, and it's attached to $validated the same way an uploaded image's path already gets attached to $validated['image'] in BookController.

Trying it out

books/show.blade.php's "Reviews" heading gets a "Write a Review" button next to it, pointing at route('books.reviews.create', $book). Fill in a rating and submit, and the review appears on the book's page immediately, right alongside the seeded ones - and the average rating and review count next to "Reviews" already update to include it, with no new code anywhere: that number was already being computed from whatever rows exist, from the moment topic 2.3 built the show page.

Try reviewing the same book a second time, and the friendly version of the error above shows up instead - "You have already reviewed this book," the rating dropdown reset to blank, back on the same form. What's still missing is a way to fix a review once it's written, or take it back entirely - that's next topic's job.
