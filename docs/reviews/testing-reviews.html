Testing reviews

Feature tests for writing, editing, and deleting a review - the same happy-path/validation-failure shape lesson 3.5 used for books, plus the one thing books never needed: proving the ownership check actually returns a 403 when someone else tries.

Unit\ReviewTest already covers the Review model itself - it belongs to a book, it belongs to a user, the unique index stops a duplicate. None of that touches a controller, a route, or the abort(403) guard topic 4.2 added. This topic closes that gap the same way 3.5 closed it for books: a new Tests\Feature\ReviewTest, proving the actual HTTP routes behave the way clicking through the app has only shown so far.

Writing a review: the happy path

public function test_a_review_can_be_created(): void
{
    $user = User::factory()->create();
    $book = Book::factory()->create();

    $response = $this->actingAs($user)->post(route('books.reviews.store', $book), [
        'rating' => 4,
        'comment' => 'Solid read.',
    ]);

    $review = Review::firstWhere(['book_id' => $book->id, 'user_id' => $user->id]);
    $response->assertRedirect(route('books.show', $book));
    $this->assertNotNull($review);
    $this->assertSame(4, $review->rating);
}

Nothing here is new mechanism - route('books.reviews.store', $book) builds the nested URL from topic 4.1's resource route exactly the way route('books.show', $book) always has, and firstWhere() with an array narrows to the one row this test actually cares about the same way BookTest's firstWhere('title', ...) already does with a single column.

Writing a review: the validation failure

public function test_creating_a_review_without_a_rating_fails_validation_and_repopulates_the_form(): void
{
    $user = User::factory()->create();
    $book = Book::factory()->create();

    $response = $this->actingAs($user)
        ->from(route('books.reviews.create', $book))
        ->post(route('books.reviews.store', $book), [
            'rating' => '',
            'comment' => 'Should not save.',
        ]);

    $response->assertRedirect(route('books.reviews.create', $book));
    $response->assertSessionHasErrors('rating');
    $response->assertSessionHasInput('comment', 'Should not save.');
    $this->assertDatabaseMissing('reviews', ['comment' => 'Should not save.']);
}

The exact same four-assertion shape 3.5 used for a book without a title: ->from() sets a real previous URL for validate()'s redirect-back to return to, assertSessionHasErrors() checks the flashed error bag, assertSessionHasInput() checks the flashed old input, and assertDatabaseMissing() confirms no half-valid row landed regardless. Only the field name and the route names changed.

Writing a review: the uniqueness failure

Books never had a second way to fail creating one - reviews do, from topic 4.1's business-rule check against an existing row rather than against the submitted fields:

public function test_reviewing_the_same_book_twice_fails_with_a_friendly_error(): void
{
    $user = User::factory()->create();
    $book = Book::factory()->create();
    Review::factory()->create(['book_id' => $book->id, 'user_id' => $user->id]);

    $response = $this->actingAs($user)->post(route('books.reviews.store', $book), [
        'rating' => 3,
    ]);

    $response->assertSessionHasErrors('rating');
    $this->assertCount(1, $book->reviews()->where('user_id', $user->id)->get());
}

This proves the friendly back()->withErrors([...]) path 4.1 wrote actually runs before the database ever gets a chance to reject the second row with the raw SQLSTATE[23000] error that topic's content quoted - the count staying at exactly 1 is the check that matters, not the error message's wording.

Editing and deleting a review, as its own author

public function test_a_review_can_be_updated_by_its_owner(): void
{
    $user = User::factory()->create();
    $review = Review::factory()->create(['user_id' => $user->id, 'rating' => 2]);

    $response = $this->actingAs($user)->put(route('reviews.update', $review), [
        'rating' => 5,
        'comment' => 'Changed my mind - loved it.',
    ]);

    $response->assertRedirect(route('books.show', $review->book));
    $this->assertSame(5, $review->fresh()->rating);
}

public function test_a_review_can_be_deleted_by_its_owner(): void
{
    $user = User::factory()->create();
    $review = Review::factory()->create(['user_id' => $user->id]);
    $book = $review->book;

    $response = $this->actingAs($user)->delete(route('reviews.destroy', $review));

    $response->assertRedirect(route('books.show', $book));
    $this->assertModelMissing($review);
}

Review::factory()->create(['user_id' => $user->id]) is worth noticing: ReviewFactory's definition() already gives every review its own factory-made book by default, so setting only user_id here is enough

  • exactly the "override just the column this test cares about" pattern BookTest already relies on throughout 3.5. $book = $review->book is read out before the delete for the same reason ReviewController@destroy itself reads it first: gone rows can't be traced back to their book afterwards. Both tests otherwise reuse fresh() and assertModelMissing() exactly as 3.5 introduced them for books, on a review instead.

Proving the 403 is real, not just a hidden button

Topic 4.2's ownership check was only ever confirmed by hand - log in as someone else, type a URL, see a "Forbidden" page. That's the one genuinely new kind of test this topic adds: three requests, each acting as a user who didn't write the review, each expecting to be turned away before anything changes:

public function test_editing_someone_elses_review_is_forbidden(): void
{
    $owner = User::factory()->create();
    $review = Review::factory()->create(['user_id' => $owner->id]);
    $someoneElse = User::factory()->create();

    $response = $this->actingAs($someoneElse)->get(route('reviews.edit', $review));

    $response->assertForbidden();
}

public function test_updating_someone_elses_review_is_forbidden(): void
{
    $owner = User::factory()->create();
    $review = Review::factory()->create(['user_id' => $owner->id, 'rating' => 3]);
    $someoneElse = User::factory()->create();

    $response = $this->actingAs($someoneElse)->put(route('reviews.update', $review), [
        'rating' => 1,
    ]);

    $response->assertForbidden();
    $this->assertSame(3, $review->fresh()->rating);
}

public function test_deleting_someone_elses_review_is_forbidden(): void
{
    $owner = User::factory()->create();
    $review = Review::factory()->create(['user_id' => $owner->id]);
    $someoneElse = User::factory()->create();

    $response = $this->actingAs($someoneElse)->delete(route('reviews.destroy', $review));

    $response->assertForbidden();
    $this->assertModelExists($review);
}

assertForbidden() is new: it's shorthand for asserting a 403 status code specifically, reading exactly as plainly as the abort(403) it's checking for. Two of the three go further than just the status code - updating's test confirms the rating actually stayed 3, and deleting's confirms the row still exists with assertModelExists() (the positive counterpart to 3.5's assertModelMissing()) - a 403 alone would still pass if authorizeOwner() somehow ran after the change instead of before it, so the real claim being tested is "nothing happened," not just "the response looked right."

One test that runs the whole thing in sequence

public function test_the_full_write_edit_delete_flow_as_the_reviews_own_author(): void
{
    $user = User::factory()->create();
    $book = Book::factory()->create();

    $createResponse = $this->actingAs($user)->post(route('books.reviews.store', $book), [
        'rating' => 3,
        'comment' => 'Decent.',
    ]);
    $review = Review::firstWhere(['book_id' => $book->id, 'user_id' => $user->id]);
    $createResponse->assertRedirect(route('books.show', $book));

    $updateResponse = $this->actingAs($user)->put(route('reviews.update', $review), [
        'rating' => 5,
        'comment' => 'Actually, loved it on a re-read.',
    ]);
    $updateResponse->assertRedirect(route('books.show', $book));
    $this->assertSame(5, $review->fresh()->rating);

    $deleteResponse = $this->actingAs($user)->delete(route('reviews.destroy', $review));
    $deleteResponse->assertRedirect(route('books.show', $book));
    $this->assertModelMissing($review);
}

The same closing move 3.5 made for books: every assertion here already appeared above in isolation, just chained - the row books.reviews.store creates is the same one reviews.update and reviews.destroy both act on next, the way actually using the app would carry it through. A bug that only shows up once a second action runs against a row a first action just created - stale $review data after a redirect, say - is exactly what the isolated tests above wouldn't catch on their own.

Lesson 4 complete

A review can be written, fixed, taken back, and found again later from /my-reviews - all of it now proven by tests that run on every future change, not just the one time each path was clicked through by hand or checked with a manual curl request. Between the four lessons so far, the catalogue can be seeded and browsed, a book can be added, edited, and deleted with its cover image kept in sync, and now a review can be written, changed, or withdrawn, always as yourself and never as anyone else.

There's still no way to find anything, though - browsing the catalogue means paging through every book in order, whatever you're actually looking for. Lesson 5 picks up from here with search: finding a book by title, author, or year instead.
