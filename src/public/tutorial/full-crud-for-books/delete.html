Delete

BookController@destroy, a spoofed DELETE request behind a confirm() dialog, and closing the orphaned-file gap the last topic left open on purpose.

Create, read, update - the catalogue can do everything except take a book back out again. This is the shortest controller method in the whole resource, and the last piece full CRUD needs.

One more route

Route::resource('books', BookController::class)->only(['index', 'show', 'create', 'store', 'edit', 'update', 'destroy']);

destroy registers a route that responds to DELETE, named books.destroy - the last of the seven actions Route::resource() can generate, and the last one this app asks for. Every method on BookController now corresponds to one.

BookController@destroy

public function destroy(Book $book)
{
    // The row and its cover image are two separate things to delete -
    // removing one never automatically removes the other. Deleting the
    // file first, while $book->image still holds its path, closes the
    // gap update() left open: a replaced cover was already an orphaned
    // file sitting in storage/app/public/books; a deleted book without
    // this line would just create another one, permanently this time.
    if ($book->image) {
        Storage::disk('public')->delete($book->image);
    }

    $book->delete();

    return redirect()->route('books.index');
}

Route model binding resolves $book the same way it does everywhere else in this controller. $book->delete() is the one line that actually matters - everything above it exists because deleting a Book row and deleting its cover image file are two unrelated operations against two different storage systems (MySQL, and the public disk), and removing one was never going to imply the other. Skip the Storage::disk('public')->delete() call, and the image file becomes exactly the same kind of orphan last topic's replaced-cover gap already left behind - just permanently this time, since nothing will ever reference that path again to make the waste visible. if ($book->image) guards against calling delete() with an empty path on a book that never had a cover in the first place.

A DELETE request, from a plain HTML button

The same problem update() had - browsers can't actually send a PUT

  • applies here too, solved the same way:
<form method="POST" action="{{ route('books.destroy', $book) }}"
      onsubmit="return confirm('Delete this book? This cannot be undone.');">
    @csrf
    @method('DELETE')
    <x-danger-button>{{ __('Delete') }}</x-danger-button>
</form>

@method('DELETE') is @method('PUT') from last topic, spoofing a different verb - same hidden input, same middleware reading it, same POST underneath. onsubmit is plain JavaScript event handling, already familiar - confirm() shows the browser's own yes/no dialog and returns true or false; returning false from onsubmit stops the form submitting at all. Cancel the dialog, and the request to books.destroy never leaves the browser - nothing server-side even knows a delete was attempted. It sits next to the "Edit" link already on books/show.blade.php's header, styled with x-danger-button (red, rather than the neutral grey every other button in this app uses) - the one action here that can't be undone by editing the result afterward.

Trying it out

Open any book, click "Delete," and confirm the dialog - the response redirects to the catalogue index, and the book is gone from it, its page, and the database, all in one request. Delete a book that has an uploaded cover, and its file disappears from storage/app/public/books too, not just the database row - checkable directly, since nothing else in the app would ever show that.

Full CRUD is done: a book can be created, read, updated, and deleted, each step validated and each failure handled without a raw database error reaching the browser. What's still missing is proof, beyond clicking around by hand, that all four keep working together as the codebase keeps changing - that's next topic's job.
