Editing and deleting your own review

A flat reviews/{review} route alongside the nested one, a shared form partial, and the manual abort(403) ownership check guarding edit, update, and destroy alike - a deliberate stand-in for the Policy class Part 2 introduces.

A review can be written now, but not fixed or taken back - the only way to change your mind about a book so far is to email the lecturer. This topic finishes the review half of CRUD: editing and deleting a review you wrote, and refusing to let anyone touch a review that isn't theirs.

A second route, flat this time

Last topic's route needed a book in the URL because creating a review only makes sense in the context of one. Editing or deleting an existing review doesn't have that problem - the review already knows which book it belongs to - so this one drops the nesting:

Route::resource('books.reviews', ReviewController::class)->only(['create', 'store']);

Route::resource('reviews', ReviewController::class)->only(['edit', 'update', 'destroy']);

Same controller, two separate Route::resource() calls - nothing stops one controller from answering to more than one resource route, and nothing requires every route touching reviews to nest the same way. edit and update resolve to GET /reviews/{review}/edit and PUT /reviews/{review}, named reviews.edit/reviews.update - directly parallel to books.edit/books.update from topic 3.3, just on a Review instead of a Book. destroy is the familiar DELETE /reviews/{review} from topic 3.4's playbook, applied here.

The ownership check: abort(403)

Nothing so far has stopped any logged-in user from typing /reviews/1/edit into the address bar, whoever wrote review 1. Every one of the three new methods needs the same answer to the same question - is this actually your review? - so it's worth writing once:

private function authorizeOwner(Review $review): void
{
    if ($review->user_id !== auth()->id()) {
        abort(403);
    }
}

abort(403) is new: it stops the request immediately and renders Laravel's built-in "403 Forbidden" error page, the same way a nonexistent {book} already renders a 404 automatically via route model binding - except this time nothing about the URL was wrong, only who's asking. $review->user_id !== auth()->id() asks the same "who is this, really" question topic 4.1's store() already asked when it set user_id from auth()->id() instead of trusting a submitted field - that was about not letting a request claim to be someone; this is about not letting a request act on someone else's row. Every one of edit(), update(), and destroy() starts by calling it:

public function edit(Review $review)
{
    $this->authorizeOwner($review);

    return view('reviews.edit', compact('review'));
}

This is worth being honest about: Laravel has a proper, built-in tool for exactly this job, called a Policy - a class dedicated to answering "can this user do this to this model?" that the framework knows how to call automatically. It isn't used here on purpose, not because it's unknown yet by accident. Reaching for it now would teach that later topic ahead of itself; abort(403) behind a private method is a plain, honest stand-in until then - you're about to meet the framework's proper way of doing this, later.

One more small reuse: validationRules()

update() needs to check the same rating/comment rules store() already checks - a review still has to make sense the second time it's saved, not just the first. BookController solved this exact problem in topic 3.3 with a private validationRules() method shared between store() and update(); the same fix applies here:

private function validationRules(): array
{
    return [
        'rating' => 'required|integer|between:1,5',
        'comment' => 'nullable|string',
    ];
}

store() from last topic is updated to call $request->validate($this->validationRules()) instead of repeating the two rule strings inline, and update() calls the exact same thing:

public function update(Request $request, Review $review)
{
    $this->authorizeOwner($review);

    $review->update($request->validate($this->validationRules()));

    return redirect()->route('books.show', $review->book);
}

$review->update(...) is the same method books/edit.blade.php's update() already calls on a Book - Eloquent's update() works the same way on any model, given an array of already-validated fields. redirect()->route('books.show', $review->book) reads the book back off the relationship rather than needing it passed in separately - the review already knows which book it belongs to, so nothing about this route needs {book} in its URL at all.

destroy(): read the relationship before it's gone

public function destroy(Review $review)
{
    $this->authorizeOwner($review);

    $book = $review->book;
    $review->delete();

    return redirect()->route('books.show', $book);
}

The one new wrinkle, compared to topic 3.4's BookController@destroy: $review->book has to be read into a local variable before $review->delete() runs. Once the row is gone, so is the foreign key that made $review->book resolvable at all - reading it after delete() would return nothing, and there'd be nowhere left to redirect to.

One shared form partial, same idea as books

reviews/create.blade.php had its own copy of the rating <select> and comment <textarea> from last topic; reviews/edit.blade.php would need the exact same markup, just pre-filled. Rather than maintaining two copies, both share one partial - the same fix books/partials/form.blade.php already applied to books.create/books.edit:

{{-- Shared between create.blade.php and edit.blade.php. $review is only set
     when editing - old('field', $review->field ?? '') falls back to the
     review's current value there, or to an empty string on create, and to
     whatever was just typed in on either page if validation just failed. --}}
<select id="rating" name="rating" ... required>
    <option value="">{{ __('Select a rating') }}</option>
    @for ($i = 1; $i <= 5; $i++)
        <option value="{{ $i }}" @selected(old('rating', $review->rating ?? '') == $i)>{{ $i }} / 5</option>
    @endfor
</select>

The only change from last topic's version is old('rating', $review->rating ?? '') instead of bare old('rating') - $review doesn't exist when the partial is included from create.blade.php, so $review->rating ?? '' quietly falls back to an empty string there, exactly the same fallback books/partials/form.blade.php already relies on for a book's title. create.blade.php now just includes it:

<form method="POST" action="{{ route('books.reviews.store', $book) }}" class="space-y-6">
    @csrf

    @include('reviews.partials.form')
</form>

and reviews/edit.blade.php includes the same partial, passing $review in, with the familiar @method('PUT') spoofing a request browsers can't send natively:

<form method="POST" action="{{ route('reviews.update', $review) }}" class="space-y-6">
    @csrf
    @method('PUT')

    @include('reviews.partials.form', ['review' => $review])
</form>

Showing the controls to their owner, and no one else

reviews/partials/review.blade.php - the partial books/show.blade.php already loops over to print every review on a book - gets an "Edit" link and a "Delete" button, but only for the review's own author:

@if ($review->user_id === auth()->id())
    <div class="flex items-center gap-3">
        <a href="{{ route('reviews.edit', $review) }}">{{ __('Edit') }}</a>

        <form method="POST" action="{{ route('reviews.destroy', $review) }}"
              onsubmit="return confirm('Delete this review? This cannot be undone.');">
            @csrf
            @method('DELETE')
            <button type="submit">{{ __('Delete') }}</button>
        </form>
    </div>
@endif

This @if is a convenience for the person looking at the page, nothing more - it hides a button someone else's request would fail anyway, the same relationship $review->user_id === auth()->id() checks that authorizeOwner() checks on the server. Hiding the button changes nothing about what's actually allowed; skip it entirely and someone could still type /reviews/1/edit into the address bar by hand and get turned away by the exact same abort(403). The delete <form> reuses topic 3.4's confirm()-guarded DELETE-spoofing pattern exactly - same @method('DELETE'), same "this cannot be undone" wording, just on a review instead of a book.

Trying it out

Open a book you've reviewed, and "Edit" and "Delete" now sit next to your own review - change the rating, save, and the book page reflects it immediately, average included. Every other review on the same page, written by someone else, shows neither button at all.

Try reaching /reviews/{id}/edit directly for a review that isn't yours - typing the URL in by hand, not clicking anything the page offers - and the response is a 403, Laravel's own "Forbidden" page, before the edit form is ever rendered. The same thing happens sending a PUT or DELETE straight to /reviews/{id} for someone else's review, with no button involved at all - the check runs in the controller, not the browser, so nothing about hiding a link is what's actually keeping anyone out.

Between the two review topics, the app can now do everything a reviewer needs: write one, fix it, or take it back, always as yourself and never as anyone else. What's still missing is a single place to see every review you've written, across every book at once - that's next topic's job.
