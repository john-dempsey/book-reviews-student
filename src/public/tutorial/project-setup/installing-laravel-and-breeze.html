Installing Laravel and Breeze

Composer and npm, Vite and asset bundling, and installing Laravel Breeze's Blade stack for real authentication.

The bare install has no way to register or log in yet — that's the first thing this lesson actually adds. Getting there means meeting two tools you haven't used before: Composer (PHP's package manager) and npm (JavaScript's). Both are already running quietly in the background of every composer install/npm run build you've typed so far; this topic is where they start doing visible work.

Composer: PHP's package manager

Laravel itself, and everything it depends on, arrived in src/ as Composer packages — you saw vendor/ get populated by composer install during first-time setup. composer.json is the list of packages a project depends on, by name and version constraint:

"require": {
    "php": "^8.2",
    "laravel/framework": "^12.0",
    "laravel/tinker": "^2.10.1"
}

composer install reads a second file, composer.lock, and installs the exact versions it records — that's what makes first-time setup reproducible across machines. composer update is different: it re-reads composer.json's version constraints, works out the newest versions that still satisfy them, and rewrites composer.lock to match. Adding a brand-new package — which is what installing Breeze means — always goes through update, since there's nothing in the lock file for a package that isn't in composer.json yet.

npm, Vite, and why there's a build step at all

package.json is Composer's JavaScript equivalent — a list of JS packages, read by npm install. The bare install already lists a few: Tailwind CSS (for styling) and Vite (the build tool). Browsers can't run Tailwind's utility classes or your .css/.js source files directly the way they are on disk — they need bundling: resolving imports, compiling Tailwind's classes into plain CSS, and writing the result to public/build/ as a handful of hashed files a Blade view pulls in with one @vite(...) directive. Vite is the tool that does that bundling.

Two npm scripts matter, both already defined in package.json:

  • npm run build — one-shot, produces the optimized files that actually ship. This is what first-time setup ran, and what you'll re-run any time you want a fresh production bundle.
  • npm run dev — starts Vite in watch mode instead: it stays running, rebuilding automatically as you edit CSS/JS, and the browser picks up the change without a manual reload. You won't need this yet — it matters once you're actively editing views — but it's worth knowing it exists, since compose.yaml already exposes the port it runs on (5173) for exactly that purpose.

The starter kit this project didn't install

laravel new (the command that created src/ before this lesson) asks which starter kit to scaffold in, alongside the questions covered in the last topic. A starter kit is a ready-made authentication setup — registration, login, and a starting frontend stack — installed in the same step as the framework itself. This project answered None, deliberately: every starter kit laravel new currently offers builds on Inertia (React, Vue, or Livewire), wiring up an SPA-shaped frontend this course isn't using.

Skipping the prompt doesn't mean skipping authentication — it means installing it separately, afterward, from a stack that fits this course: Laravel Breeze.

Installing Breeze

Breeze isn't part of the starter-kit prompt above; it's an ordinary Composer package, added like any other:

composer require laravel/breeze --dev

--dev marks it a development-only dependency — Breeze generates auth code into your app once, it isn't something the running app loads at request time, so it has no business shipping to a production install the way laravel/framework does. Breeze's own installer then does the actual scaffolding, and takes one argument: which frontend stack to generate:

php artisan breeze:install blade

blade is the stack this app uses throughout — plain Blade views and controllers, no Inertia, matching the "None" choice above. (Breeze also offers react, vue, and api stacks; not used here.) That one command generated the auth routes, views, and controller, then ran npm install and npm run build on its own, so the styled result is ready to view immediately.

What actually landed

  • routes/auth.php — registration, login, logout, and password-reset routes, required from the bottom of routes/web.php.
  • resources/views/auth/ — a Blade view per route above; dashboard.blade.php and resources/views/profile/ for a logged-in user's own account page.
  • app/Http/Controllers/Auth/ and ProfileController.php — the controllers those routes call.
  • tests/Feature/Auth/ and ProfileTest.php — Breeze ships its own feature tests for every route it just generated.

Nothing about the database changed — Breeze's Blade stack reuses the users migration laravel new already created, so there's nothing new to migrate here. One smaller, purely cosmetic change is worth naming so it doesn't look like a mistake later: Breeze's installer replaced the bare install's Tailwind v4 setup (a plugin in vite.config.js, configured via an @theme block in app.css itself) with the older tailwind.config.js

  • postcss.config.js pair and Tailwind v3 — Breeze's Blade stack still targets that setup. Both are Tailwind; only the configuration shape differs.

None of this touches authorization — who's allowed to do what. Breeze only answers who's logged in, the same distinction raised at the start of this lesson.

Checking it worked

http://localhost:8080/register and http://localhost:8080/login now render real, styled forms instead of 404s, and registering an account redirects straight to /dashboard — a route routes/web.php protects with ->middleware(['auth', 'verified']), so it's reachable only once you're actually logged in. php artisan test is worth re-running here too: Breeze's own auth tests join the suite, and everything should still pass with no schema changes required.
