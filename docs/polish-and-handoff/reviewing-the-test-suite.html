Reviewing the test suite

A controller-by-controller pass over everything Lessons 1 through 6 have tested so far, turning up one real gap - the my-reviews page has never actually been tested - and closing it with five new tests.

The last topic proved something specific: every read route's query count stays flat as its data grows. That's one property, checked on five pages. It says nothing about whether the suite as a whole still matches what the app actually does - whether every controller action has a test behind it, and whether every test that exists is still checking something real. This topic is that pass: walk the suite one controller at a time, and close whatever turns up.

Books and authors: nothing missing

Tests\Feature\BookTest covers BookController action by action: index (the plain list, three search branches, the no-match message, the repopulated search box), show (authors and reviews rendered, a 404 for a book that doesn't exist), create/store (success, and a missing title failing validation with the form repopulated), edit/update (the same shape), and destroy (the row gone, and its cover image gone from storage with it). Tests\Feature\AuthorTest does the same for AuthorController's two actions, index and show - the only two it has, since authors were never given their own create/edit/delete routes. Nothing here needs closing; this pass just confirms it.

Reviews: one action never got a test at all

ReviewController has five actions wired to routes: create/store, edit/update, destroy, and mine. Tests\Feature\ReviewTest covers the first four thoroughly - success, validation failure, the duplicate-review guard, and a someoneElse user forbidden from editing, updating, or deleting a review they don't own. mine - the page behind "My Reviews" in the navigation - has no test in that file at all.

It isn't completely unexercised. QueryCountTest visits route('reviews.mine') twice, at three reviews and at fifteen, and asserts the query count came back the same both times. But that test only ever creates reviews belonging to the one user it acts as - it never checks whose reviews come back, just how many queries it took to fetch them. A version of mine() that listed every review in the database, not just the logged-in user's own, would pass QueryCountTest exactly as well as the real one does. A flat query count and a correct result are two different claims, and only one of them has ever been tested.

Closing the gap

Five tests, added to the bottom of Tests\Feature\ReviewTest - the same file already covering the rest of ReviewController, since mine() belongs to that controller too, not a new one of its own.

public function test_guests_are_redirected_to_login_from_my_reviews(): void
{
    $response = $this->get(route('reviews.mine'));

    $response->assertRedirect(route('login', absolute: false));
}

The same shape BookTest and AuthorTest both open with - every route in the app sits behind auth middleware, and mine() had never had this checked either.

public function test_my_reviews_lists_the_users_own_reviews(): void
{
    $user = User::factory()->create();
    $book = Book::factory()->create(['title' => 'Dune']);
    Review::factory()->create([
        'book_id' => $book->id,
        'user_id' => $user->id,
        'rating' => 5,
        'comment' => 'A genuine classic.',
    ]);

    $response = $this->actingAs($user)->get(route('reviews.mine'));

    $response->assertOk();
    $response->assertSee('Dune');
    $response->assertSee('A genuine classic.');
    $response->assertSee('5 / 5');
}

The baseline claim the page makes at all: a logged-in user's own review shows up, with the book it's attached to, its comment, and its rating. Nothing here is new as a technique - it's the same assertSee() pattern every other index/show test in the suite already uses - which is exactly why it's notable that nobody had written it yet.

public function test_my_reviews_does_not_list_another_users_reviews(): void
{
    $user = User::factory()->create();
    $someoneElse = User::factory()->create();
    Book::factory()->create(['title' => 'My Book'])
        ->reviews()->create(['user_id' => $user->id, 'rating' => 4]);
    Book::factory()->create(['title' => 'Someone Elses Book'])
        ->reviews()->create(['user_id' => $someoneElse->id, 'rating' => 2]);

    $response = $this->actingAs($user)->get(route('reviews.mine'));

    $response->assertSee('My Book');
    $response->assertDontSee('Someone Elses Book');
}

This is the one that actually matters, and the one QueryCountTest was never in a position to catch: two users, two reviews, and a check that each user's page only ever shows their own. assertDontSee() does the real work here, the same way it did for search results back in Lesson 5

  • assertSee('My Book') alone would still pass even if the page leaked every review in the database.
public function test_my_reviews_shows_the_most_recently_written_review_first(): void
{
    $user = User::factory()->create();
    $older = Book::factory()->create(['title' => 'Older Review']);
    $newer = Book::factory()->create(['title' => 'Newer Review']);
    Review::factory()->create([
        'book_id' => $older->id,
        'user_id' => $user->id,
        'created_at' => now()->subDay(),
    ]);
    Review::factory()->create([
        'book_id' => $newer->id,
        'user_id' => $user->id,
        'created_at' => now(),
    ]);

    $response = $this->actingAs($user)->get(route('reviews.mine'));

    $response->assertSeeInOrder(['Newer Review', 'Older Review']);
}

mine()'s own doc comment promises "most recent first" - that's what ->latest() is there for - but nothing checked it actually held. assertSeeInOrder() is new here: it doesn't just check that both titles appear somewhere in the response, it checks that the first one appears before the second in the raw HTML, which is exactly what "most recent first" means on a rendered page.

public function test_my_reviews_shows_a_message_when_the_user_has_no_reviews(): void
{
    $user = User::factory()->create();

    $response = $this->actingAs($user)->get(route('reviews.mine'));

    $response->assertOk();
    $response->assertSee("You haven't reviewed any books yet.");
}

The @forelse/@empty branch in reviews/mine.blade.php has had its own wording since the page was built - the same kind of exact-text check books.index's "No books match" message got in Lesson 5, now applied to the one empty state that had gone unchecked.

Proving it: temporarily un-scope the query

Same discipline as the last topic - a test that would pass either way isn't proving anything. mine() currently reads:

$reviews = auth()->user()->reviews()
    ->with('book')
    ->latest()
    ->paginate(12);

Swapping auth()->user()->reviews() for a plain Review::query() - every review in the table, not just the logged-in user's - and rerunning just the scoping test:

Not to contain: Someone Elses Book

test_my_reviews_does_not_list_another_users_reviews fails immediately, exactly as it should. Putting auth()->user()->reviews() back drops the suite straight back to green - confirmation that this test really is watching the one property that matters, not just exercising the route.

Running everything

Tests:    83 passed (200 assertions)

Five new tests, all in Tests\Feature\ReviewTest, alongside everything carried over from Lessons 1 through 6.1 - up from 78. Every action on every controller in the app now has a test confirming what it actually does, not just how many queries it takes to do it.
