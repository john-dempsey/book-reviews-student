Testing the full CRUD flow

Feature tests for store, update, and destroy - a validation failure that actually repopulates the form, a cover image that actually leaves storage, and one test that runs create, edit, and delete back to back.

Full CRUD is done, but only proven by clicking around a browser - add a book, fix its title, delete it, and trust that each step actually did what it looked like it did. Last lesson's testing topic covered the two read-only routes the same way; this topic closes the same gap for the three that actually change data, and adds one test that runs all three in sequence, the way a person using the app actually would.

Creating a book: the happy path

Tests\Feature\BookTest already has four methods from last lesson. The first new one posts to books.store the same way the form does, and checks the book actually landed:

public function test_a_book_can_be_created(): void
{
    Storage::fake('public');
    $user = User::factory()->create();

    $response = $this->actingAs($user)->post(route('books.store'), [
        'title' => 'Project Hail Mary',
        'year' => 2021,
        'image' => UploadedFile::fake()->image('cover.jpg'),
    ]);

    $book = Book::firstWhere('title', 'Project Hail Mary');
    $response->assertRedirect(route('books.show', $book));
    $this->assertNotNull($book);
    Storage::disk('public')->assertExists($book->image);
}

Two things here haven't come up before. Storage::fake('public') swaps the real public disk for a temporary one that exists only for the duration of this test - nothing this test uploads ever touches storage/app/public for real, and the fake disk (along with whatever got "saved" to it) is thrown away automatically once the test ends. UploadedFile::fake()->image('cover.jpg') builds a real, valid image file entirely in memory to stand in for one a user would have picked in a file input - $request->hasFile('image') and the image validation rule both treat it exactly like the real thing. assertExists() on the faked disk confirms putFile() actually wrote something to it, not just that the redirect looked right.

Creating a book: the validation failure

The interesting case isn't the happy path - it's proving that a bad submission behaves the way topic 3.2 described, rather than just looking like it does when clicking through a browser once:

public function test_creating_a_book_without_a_title_fails_validation_and_repopulates_the_form(): void
{
    $user = User::factory()->create();

    $response = $this->actingAs($user)
        ->from(route('books.create'))
        ->post(route('books.store'), [
            'title' => '',
            'year' => 2021,
        ]);

    $response->assertRedirect(route('books.create'));
    $response->assertSessionHasErrors('title');
    $response->assertSessionHasInput('year', 2021);
    $this->assertDatabaseMissing('books', ['year' => 2021]);
}

->from() is new: it sets the session's "previous URL" before the request runs, the same thing actually visiting /books/create first would do - validate()'s automatic redirect-back needs somewhere to redirect back to, and without this a test request has no real previous page to return to. assertSessionHasErrors('title') checks the flashed error bag directly, the same data $errors->get('title') reads in the view. assertSessionHasInput('year', 2021) checks the flashed old input the same way old('year') reads it - proof that repopulation isn't just a visual impression from typing into a form by hand, but a real, checkable guarantee. assertDatabaseMissing() closes the loop: whatever else happened, no half-valid row made it into books.

Editing a book: both cases again

update() shares its validation rules with store(), so both cases repeat here, shorter now that the pattern's established:

public function test_a_book_can_be_updated(): void
{
    $user = User::factory()->create();
    $book = Book::factory()->create(['title' => 'Old Title']);

    $response = $this->actingAs($user)->put(route('books.update', $book), [
        'title' => 'New Title',
        'year' => $book->year,
    ]);

    $response->assertRedirect(route('books.show', $book));
    $this->assertSame('New Title', $book->fresh()->title);
}

$this->put() sends the request as a real PUT - the test client talks to the routing layer directly, so there's no browser here needing @method('PUT')'s hidden-input trick at all; that's purely a problem for an actual <form> tag. $book->fresh() re-fetches the row from the database rather than trusting the $book variable already held in memory, which still shows whatever it was populated with; only a fresh read proves the UPDATE really happened.

public function test_updating_a_book_without_a_title_fails_validation_and_leaves_it_unchanged(): void
{
    $user = User::factory()->create();
    $book = Book::factory()->create(['title' => 'Dune']);

    $response = $this->actingAs($user)->put(route('books.update', $book), [
        'title' => '',
        'year' => $book->year,
    ]);

    $response->assertSessionHasErrors('title');
    $this->assertSame('Dune', $book->fresh()->title);
}

Same shape as the creation failure, with one addition worth the assertion: a failed update() has an existing row already sitting in the database, and the test proves it stayed exactly as it was rather than getting partially overwritten before validation ran.

Deleting a book, and its cover image with it

public function test_a_book_can_be_deleted(): void
{
    $user = User::factory()->create();
    $book = Book::factory()->create();

    $response = $this->actingAs($user)->delete(route('books.destroy', $book));

    $response->assertRedirect(route('books.index'));
    $this->assertModelMissing($book);
}

assertModelMissing() checks the same thing assertDatabaseMissing() would, built directly from the model instance instead of a raw table => attributes array - one less place to accidentally typo a column name. The more interesting claim from last topic - that deleting a book deletes its cover file too, not just its row - gets its own test:

public function test_deleting_a_book_removes_its_cover_image_from_storage(): void
{
    Storage::fake('public');
    $user = User::factory()->create();
    $path = UploadedFile::fake()->image('cover.jpg')->store('books', 'public');
    $book = Book::factory()->create(['image' => $path]);

    $this->actingAs($user)->delete(route('books.destroy', $book));

    Storage::disk('public')->assertMissing($path);
}

->store('books', 'public') here does directly what BookController normally does through putFile() - saves a fake image to the faked disk and returns its path - so the test can start from a book that already has a cover, without going through the store() route just to set one up. assertMissing() is assertExists()'s opposite: proof that BookController@destroy's Storage::disk('public')->delete($book->image) line actually ran, not just that the row disappeared.

One test that proves the whole flow together

Every test so far checks one action in isolation, each starting from its own freshly-seeded state. This topic's title promises something slightly different - that create, edit, and delete keep working as a sequence, the same book carried through all three, the way someone actually using the app would experience it:

public function test_the_full_create_edit_delete_flow(): void
{
    $user = User::factory()->create();

    $createResponse = $this->actingAs($user)->post(route('books.store'), [
        'title' => 'The Fellowship of the Ring',
        'year' => 1954,
    ]);
    $book = Book::firstWhere('title', 'The Fellowship of the Ring');
    $createResponse->assertRedirect(route('books.show', $book));

    $editResponse = $this->actingAs($user)->put(route('books.update', $book), [
        'title' => 'The Fellowship of the Ring (Revised)',
        'year' => 1954,
    ]);
    $editResponse->assertRedirect(route('books.show', $book));
    $this->assertSame('The Fellowship of the Ring (Revised)', $book->fresh()->title);

    $deleteResponse = $this->actingAs($user)->delete(route('books.destroy', $book));
    $deleteResponse->assertRedirect(route('books.index'));
    $this->assertModelMissing($book);
}

Nothing in this method is a new assertion - every line has already appeared above, just chained: the id books.store hands back is the same one books.update and books.destroy both act on next, exactly as $book would be reused clicking through the real pages in the same order. A regression that only shows up when one action runs after another - an id that stops carrying through correctly, say - is exactly the kind of bug the isolated tests above wouldn't catch on their own, and this one would.

Every test written since Lesson 1 still passes alongside them: the full suite now proves the catalogue can be seeded, browsed, and changed - created, edited, deleted, cover image and all - without a single click through the browser required to believe it.

Lesson 3 complete

A book can be added, validated, edited with its cover image kept or replaced, and deleted along with that cover - each step now checked by a test that runs on every future change, not just the one time it was clicked through by hand. The catalogue itself is finished. What it's still missing is the other half of "book reviews": an actual way to leave one.
