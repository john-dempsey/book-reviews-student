Seeders and demo data

Turning last topic's ad hoc factory calls into a repeatable command that builds a whole believable catalogue in one go - one seeder per model, wired together in an order that matters, and the ReviewFactory default that has to be worked around to make it happen.

Everything the last topic built - AuthorFactory, BookFactory, ReviewFactory - still only runs when someone types a command in tinker. Nothing produces the whole catalogue at once: a fixed number of users and authors, books attached to the right authors, reviews attached to the right books and users, all in one go. That's what a seeder does - a class that scripts a batch of factory calls (and whatever else is needed) into one repeatable command.

Creating a seeder

php artisan make:seeder AuthorSeeder

<?php

namespace Database\Seeders;

use Illuminate\Database\Console\Seeds\WithoutModelEvents;
use Illuminate\Database\Seeder;

class AuthorSeeder extends Seeder
{
    /**
     * Run the database seeds.
     */
    public function run(): void
    {
        //
    }
}

An empty run() method, waiting to be filled in - the generator also imports WithoutModelEvents, a trait that's only actually needed on the top-level DatabaseSeeder (more on that below), so that unused import gets deleted from every seeder except the one that needs it.

Rather than writing everything inside DatabaseSeeder directly, this app gets one seeder per model - UserSeeder, AuthorSeeder, BookSeeder, ReviewSeeder - the same instinct as one migration per table back in Lesson 1: each file stays short enough to read in one glance, and it's obvious which one to open when only the reviews need changing.

The two simplest ones barely do more than call a factory:

// AuthorSeeder.php
public function run(): void
{
    Author::factory(5)->create();
}

// UserSeeder.php
public function run(): void
{
    $users = [
        ['name' => 'Emma Watson', 'email' => 'emma.watson84@example.com'],
        ['name' => "Liam O'Connor", 'email' => 'liam.oconnor22@example.com'],
        // ...
    ];

    foreach ($users as $user) {
        User::factory()->create($user);
    }
}

UserSeeder overrides name and email on every call so the five accounts are recognisable rather than randomly generated - everything else (the password, the verified-at timestamp) still comes from UserFactory's definition(), exactly as Book::factory()->create(['title' => 'Dune']) worked in the last topic.

Wiring them together: DatabaseSeeder

php artisan db:seed only ever runs one class directly - DatabaseSeeder - so that's where the four seeders above actually get called, via $this->call():

public function run(): void
{
    $this->call([
        UserSeeder::class,
        AuthorSeeder::class,
        BookSeeder::class,
        ReviewSeeder::class,
    ]);
}

$this->call() runs each listed seeder's run() method in the exact order given. DatabaseSeeder stays a short table of contents rather than a place where actual seeding logic lives - which also means this is the one seeder that keeps the WithoutModelEvents trait from the generated skeleton above: it applies to the whole batch, not to any one seeder individually.

Why that order isn't arbitrary

Swap two of those lines - say, run BookSeeder before AuthorSeeder - and seeding fails immediately:

Database\Seeders\BookSeeder ........................................ RUNNING

InvalidArgumentException

You requested 1 items, but there are only 0 items available.

at database/seeders/BookSeeder.php:26

BookSeeder asks for Author::all() and then attaches a random one to every book. Run it before AuthorSeeder, and Author::all() comes back empty - there's nothing yet to pick a random one from. The rule this follows is the same one from designing the schema back in Lesson 1: strong entities before the weak entities that depend on them. Users and authors don't need anything else to exist first; books do (an author, to attach to); reviews depend on the most, needing both a book and a user already in place. Seed in that order - users, authors, books, reviews - and every later seeder finds exactly what it needs already sitting in the database.

BookSeeder: attaching authors that already exist

public function run(): void
{
    $authors = Author::all();

    $books = Book::factory(20)->create();

    // Most books have a single author.
    $books->each(function (Book $book) use ($authors) {
        $book->authors()->attach($authors->random());
    });

    // A couple of books are co-written - attach a second, different
    // author to two randomly chosen books.
    $books->random(2)->each(function (Book $book) use ($authors) {
        $firstAuthorId = $book->authors->first()->id;

        $secondAuthor = $authors
            ->reject(fn (Author $author) => $author->id === $firstAuthorId)
            ->random();

        $book->authors()->attach($secondAuthor);
    });
}

$authors = Author::all() only makes sense given the ordering rule above - it's the five rows AuthorSeeder already created. Twenty books get created first, unattached to anyone; then every book gets exactly one random existing author attached via $book->authors()->attach(), the same many-to-many method from the Eloquent relationships topic. Two books, chosen at random, get a second author attached afterwards - reject() filters that second pick down to authors who aren't already attached to this particular book, so a book can never end up "co-written" with itself.

ReviewSeeder: working around the factory's own default

Last topic's ReviewFactory gives book_id and user_id a default worth revisiting here:

// ReviewFactory.php
'book_id' => Book::factory(),
'user_id' => User::factory(),

That default is exactly what makes Review::factory()->create() useful on its own in tinker - it always produces a complete row, inventing a book and a user to go with it if none are supplied. Inside a seeder, that's the opposite of helpful. Twenty books and five users already exist, created on purpose, in a specific quantity - a review seeder that let every review invent its own extra book and user would blow both those numbers open. It's easy to see happen:

> App\Models\Book::count(); App\Models\User::count();
= 20
= 5
> App\Models\Review::factory()->create();
> App\Models\Book::count(); App\Models\User::count();
= 21
= 6

One unguarded Review::factory()->create() call, and there's a 21st book and a 6th user that nobody asked for. ReviewSeeder avoids this by never calling Review::factory()->create() without overriding both foreign keys:

public function run(): void
{
    $users = User::all();
    $books = Book::all();

    $reviewCounts = [
        0, 0,
        5, 5, 5, 5,
        4, 4, 4, 4,
        3, 3, 3, 3,
        2, 2, 2, 2, 2, 2,
    ];
    shuffle($reviewCounts);

    $books->each(function (Book $book, int $index) use ($users, $reviewCounts) {
        $reviewerCount = $reviewCounts[$index];

        if ($reviewerCount === 0) {
            return;
        }

        $users->random($reviewerCount)->each(function (User $user) use ($book) {
            Review::factory()->create([
                'book_id' => $book->id,
                'user_id' => $user->id,
            ]);
        });
    });
}

Passing 'book_id' => $book->id and 'user_id' => $user->id overrides the factory's defaults completely - Book::factory() and User::factory() never run, because the values they'd have filled in are already supplied. Only rating and comment still come from ReviewFactory's own Faker calls.

The rest of the method controls how many reviews land on each book. $reviewCounts is twenty numbers, one per book, that always add up to sixty and stay within 0-5; shuffle() means it isn't always the same two books that end up with none. For whichever count a given book gets, $users->random($reviewerCount) picks that many different users out of the five - never the same user twice for the same book, which matters because reviews has a unique index on book_id + user_id (from the migrations topic back in Lesson 1) that would reject a second review by the same user on the same book outright.

Running it

php artisan migrate:fresh --seed

drops every table, re-runs all the migrations, and then runs DatabaseSeeder - the command to reach for any time the schema or the seeders themselves have changed, and the one used throughout this topic. php artisan db:seed on its own re-runs just the seeding half, without touching the schema - which only works once. Run it a second time against data that's already there, and it fails the same way a form re-submitted twice would:

Illuminate\Database\UniqueConstraintViolationException

SQLSTATE[23000]: Integrity constraint violation: 1062 Duplicate entry
'emma.watson84@example.com' for key 'users.users_email_unique'

UserSeeder tries to insert emma.watson84@example.com again, and the same unique constraint that stops two people registering with the same email stops the seeder too. While working on just one seeder, db:seed --class= targets a single one instead of the whole batch - handy for, say, tweaking BookSeeder without waiting on UserSeeder and AuthorSeeder to run again first:

php artisan db:seed --class=BookSeeder

Checking the result

$ php artisan tinker
> App\Models\User::count();
= 5
> App\Models\Author::count();
= 5
> App\Models\Book::count();
= 20
> App\Models\Review::count();
= 60
> App\Models\Book::has('authors', '>=', 2)->count();
= 2
> App\Models\Book::doesntHave('reviews')->count();
= 2

Five users, five authors, twenty books, sixty reviews, two co-written books, two books with no reviews yet - exactly the shape this topic set out to build, and all of it reproducible from nothing with one command.

What's still missing

The catalogue is real now, but there's still no way to actually browse it - no page lists the books, no page shows one book's authors and reviews. That's this lesson's next topic.
