Confirming eager loading solved N+1

Every controller since Lesson 2 chose to eager-load its relationships rather than let Blade fetch them lazily - this topic writes the regression test that confirms that decision actually paid off, and looks at what eager loading trades away to get there.

Every read route in this app - the catalogue, a single book, the author list, a single author, a user's own reviews - has quietly made the same choice since Lesson 2: load whatever a page's relationships are going to need up front, in one extra query, rather than letting Blade fetch them one row at a time as it renders. BookController@index's own comment has called this out by name since the day it was written - "avoids the N+1 problem." This topic doesn't introduce that decision; it confirms it actually worked, with a test that would fail the day it stopped being true, instead of a comment nobody's checking.

Eager loading vs. lazy loading

Eloquent can fetch a related model two ways, and the difference between them is the entire reason this topic has anything to prove.

Lazy loading is the default: a relationship defined on a model (Book::authors(), say) fetches nothing until something actually reads it. $book->authors runs a query the first time it's touched, and not before - fine, even ideal, for a single model loaded once, like books.show's own $book. The same access pattern inside a loop over many rows is a different story: @foreach ($books as $book) touching $book->authors once per iteration runs once query per book, on top of the one that fetched the books themselves - the N+1 pattern this app has spent five lessons deliberately avoiding.

Eager loading front-loads the same relationship for every row a listing is about to render, in one extra query, run exactly once no matter how many rows are on the page: Book::with('authors') for a fresh query, $book->load('authors') for a model already fetched. That one choice, made consistently since Lesson 2, is the reason this app has no N+1 queries left to find.

Neither approach is simply better - it's a real trade-off:

  • Eager loading's advantages: a flat, predictable query count no matter how many rows are on the page - the exact property this topic's tests check for - and fewer round trips to the database overall, which usually costs more real-world latency than the number of rows those round trips return.
  • Eager loading's disadvantages: it has to be told in advance exactly what a view is going to need. A Blade template that starts touching a new relationship later needs its controller updated to match, or the N+1 this app has avoided so carefully creeps straight back in - precisely the regression QueryCountTest exists to catch. It can also over-fetch: books.show's $book->reviews->avg('rating') pulls every one of a book's review rows into memory just to average them in PHP, rather than asking the database for the average directly the way withAvg() already does on the catalogue listing.
  • Lazy loading's advantages: nothing has to be predicted ahead of time, and a relationship only costs a query at all if the page actually ends up using it - for a single model touched once, that's not a real cost either way, and it's simpler to write.
  • Lazy loading's disadvantages: the moment that same access happens inside a loop over many rows, "only costs a query if used" becomes "costs one query per row," and nothing about the code itself changes to show it - $book->authors reads identically whether $book came from a loop of one or a loop of a thousand. The bug is invisible at the call site; it only shows up as a page that quietly gets slower as the catalogue grows.

Counting queries in a test

private function countQueries(callable $fn): int
{
    DB::enableQueryLog();
    DB::flushQueryLog();

    $fn();

    $count = count(DB::getQueryLog());
    DB::disableQueryLog();

    return $count;
}

DB::enableQueryLog() turns on a running list of every query Laravel sends to the database; flushQueryLog() empties whatever's already in it, so the count that follows only reflects $fn()'s own queries, not anything left over from setting up the test. getQueryLog() returns that list - count() on it is the number this test actually cares about. Wrapping the whole sequence in a reusable private method matters here for the same reason scopeSearch() mattered in Lesson 5: every test below needs this exact sequence, and writing it once means getting it right once.

The test that matters: scale it up and compare

public function test_the_books_index_page_runs_the_same_number_of_queries_regardless_of_catalogue_size(): void
{
    $user = User::factory()->create();

    $this->seedBooks(3);
    $withThreeBooks = $this->countQueries(fn () => $this->actingAs($user)->get(route('books.index')));

    $this->seedBooks(12); // 15 books total now
    $withFifteenBooks = $this->countQueries(fn () => $this->actingAs($user)->get(route('books.index')));

    $this->assertSame($withThreeBooks, $withFifteenBooks);
}

seedBooks() is a private helper that creates however many books it's asked for, each attached to two shared authors and given two reviews - enough relationships hanging off each book that a lazy-loaded N+1 anywhere in the chain would show up. The test then visits books.index twice, once at three books and once at fifteen, and asserts the query count came back the same both times. No number is hardcoded anywhere in the assertion - deliberately. Writing $this->assertSame(3, $withThreeBooks) would also pass today, but it would just as surely start failing the day someone adds one entirely legitimate new query to the page (a feature flag lookup, another aggregate), for a reason that has nothing to do with eager loading at all. Comparing two scales against each other, instead of against a fixed number, tests the actual property eager loading promises - flat against catalogue size - without being fragile to everything else.

Four more tests repeat the exact same shape, one per remaining read route, each varying whatever quantity would expose that page's own possible N+1: books.show compares a book with three reviews against one with fifteen, authors.index compares three authors against fifteen, authors.show compares one author with three books against one with fifteen, and reviews.mine compares a user with three reviews against one with fifteen. All five live together in one new file, Tests\Feature\QueryCountTest - this is the first test class in the course that isn't about one entity's own controller, so it gets a file of its own rather than joining BookTest, AuthorTest, or ReviewTest.

Proving the test itself is real

A test that always passes is worth exactly as much as no test at all. Before trusting this one, it's worth switching BookController@index back to lazy loading on purpose - removing Book::with('authors') - and watching the test actually fail:

Failed asserting that 14 is identical to 5.

Three books rendered with authors left to load lazily cost 5 queries (2 to paginate, plus one lazy authors query per book on the page); fifteen books - only twelve of which fit on paginate(12)'s first page

  • cost 14 (the same 2, plus one per visible book, not per book in the whole catalogue). Putting with('authors') back drops both numbers straight back to a flat 3, matching every other read page in this app. That's the failure this test exists to catch - not today, since nothing here is actually broken, but the day a future change quietly swaps eager loading back out for the lazy default and nobody happens to notice a page got a little slower.

Every read page this app has now has a test confirming eager loading kept its promise - a flat query count regardless of how much data sits behind the page - not just a comment claiming it does.
