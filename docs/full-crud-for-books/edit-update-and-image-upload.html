Edit, update, and image upload

edit/update mirror create/store almost exactly - the interesting new ground is a form shared between the two pages, and a cover image saved to Laravel's public disk.

Books can be added now, correctly validated. They still can't be changed once they exist - fixing a typo in a title, or giving a book an actual cover image instead of the placeholder, both mean going nowhere near the app. This topic adds both.

Two more routes, and a routing wrinkle worth naming

Route::resource('books', BookController::class)->only(['index', 'show', 'create', 'store', 'edit', 'update']);

edit registers GET /books/{book}/edit, named books.edit - a form, same shape as create's. update registers a route that responds to PUT (and PATCH), named books.update - where that form submits to.

Browsers can only ever send GET or POST from an HTML <form> - there's no method="PUT" a browser will actually honour. Laravel's answer is @method('PUT'): a hidden input, rendered inside the form, that Laravel's own routing middleware reads and treats as if the request had actually arrived as a PUT. The request is a POST at the network level the whole time - @method is a polite fiction the framework maintains consistently on both ends, not a real HTTP verb change.

public function edit(Book $book)
{
    return view('books.edit', compact('book'));
}

Route model binding does the same job here it always has - {book} in the URL resolves straight to the $book parameter, no lookup written by hand.

One form, two pages

create.blade.php and edit.blade.php were about to become the same form twice over, save for the URL it posts to and one hidden @method('PUT') - copy-pasting it would mean every future change to a field (a new one added, a validation message reworded) has to happen in two places and stay in sync by hand. books/partials/form.blade.php exists so it doesn't have to: every input, label, and x-input-error lives there once, and each page includes it.

{{-- create.blade.php --}}
<form method="POST" action="{{ route('books.store') }}" enctype="multipart/form-data" class="space-y-6">
    @csrf

    @include('books.partials.form')
</form>

{{-- edit.blade.php --}}
<form method="POST" action="{{ route('books.update', $book) }}" enctype="multipart/form-data" class="space-y-6">
    @csrf
    @method('PUT')

    @include('books.partials.form', ['book' => $book])
</form>

create.blade.php never has a $book at all; edit.blade.php passes one in explicitly. The partial itself has to work either way - that's what old('title', $book->title ?? '') is for:

<x-text-input id="title" name="title" type="text" class="mt-1 block w-full"
              value="{{ old('title', $book->title ?? '') }}" required autofocus />

old()'s second argument is the value to fall back to when nothing's flashed to the session under that key - which is every time except right after a failed validation on this exact page. On create, there's no $book, so the fallback is '' - an empty field, same as before this topic. On edit, the fallback is $book->title - the book's actual saved value, so the form opens pre-filled with what's already there instead of a wall of blank inputs. Either way, a failed submission still repopulates whatever was actually typed, exactly as it did on the create-only form last topic - old() always wins when there's something flashed, regardless of which page it's on.

This is the same old()/error-repopulation idea from last topic, doing double duty across two pages instead of one - the direct framework-provided version of writing that fallback logic by hand twice, once per page, the way the PHP module's own form-repopulation functions would have had to.

BookController@update

public function update(Request $request, Book $book)
{
    // Same rules as store() - a book still has to make sense the second
    // time it's saved, not just the first. validationRules() below is
    // what keeps that "same rules" true by construction rather than by
    // remembering to copy a change into both methods.
    $validated = $request->validate($this->validationRules());

    if ($request->hasFile('image')) {
        $validated['image'] = Storage::disk('public')->putFile('books', $request->file('image'));
    }

    $book->update($validated);

    return redirect()->route('books.show', $book);
}

Route model binding hands update() an already-loaded $book, the same way show() and edit() get theirs - no separate lookup. $book->update($validated) is the same $fillable-guarded mass assignment Book::create() used in store(), just against an existing row instead of a new one.

store() and update() need exactly the same rules - a book has to make sense the same way whichever one saves it - so the rule array itself moved out to its own method, called from both:

private function validationRules(): array
{
    return [
        'title' => 'required|string|max:255',
        'description' => 'nullable|string',
        'year' => 'required|integer|digits:4',
        'isbn' => 'nullable|string|max:255',
        'publisher' => 'nullable|string|max:255',
        'edition_number' => 'nullable|string|max:255',
        'price' => 'nullable|numeric|min:0',
        'image' => 'nullable|image|max:2048',
    ];
}

store()'s own call becomes $request->validate($this->validationRules())

  • still the same inline validate() call this app has used since the last topic, just handed an array built by a private helper instead of typed out in place a second time. Adding a rule, or changing one, now only ever happens in one place, and store() and update() can't quietly drift apart from each other by someone editing one and forgetting the other.

Cover images: the public disk

image gets its own validation rule - nullable|image|max:2048 - the first rule this app has needed that isn't checking a plain string or number. image rejects anything that isn't actually a real image file (not just a filename that looks like one); max:2048 caps it at 2048 KB. Uploaded files also need the form itself to cooperate: enctype="multipart/form-data" on the <form> tag is what tells the browser to actually attach the file's bytes to the request - without it, only the filename would arrive, and $request->hasFile('image') would never be true no matter what was selected.

if ($request->hasFile('image')) {
    $validated['image'] = Storage::disk('public')->putFile('books', $request->file('image'));
}

Storage::disk('public') is Laravel's storage abstraction pointed at one specific place to keep files: storage/app/public on disk - not public/ directly, and not the default disk this app otherwise uses (that stays local, unrelated to this). putFile('books', ...) saves the upload under a books/ subfolder there, picks a random filename itself (never trust a user-supplied one), and returns the path it chose

  • books/a1b2c3d4....jpg - which is what gets saved to the image column. Wrapping the whole thing in hasFile() matters: editing a book without touching the file input at all must leave its existing cover alone, not overwrite it with nothing.

storage/app/public isn't inside public/ - the one folder Apache actually serves - so nothing in it is reachable by a browser yet. One command fixes that, run once per environment:

php artisan storage:link

This creates public/storage as a symlink pointing at storage/app/public - the same folder, reachable two ways. Everything already saved there becomes servable immediately, with no code change and nothing to move.

Rendering it: Storage::url()

<img src="{{ $book->image ? Storage::url($book->image) : asset('images/book-placeholder.png') }}"
     alt="Cover of {{ $book->title }}" ...>

$book->image only ever holds the path putFile() returned - books/a1b2c3d4....jpg - not something a browser can load directly. Storage::url() turns that stored path into the actual /storage/... URL the symlink makes servable, the one canonical way this app turns a stored path back into something an <img> tag can use - both the book's own show page and its card on the catalogue index use it the same way, falling back to the same placeholder used before any book had a real cover.

Trying it out

books/show.blade.php's header gets an "Edit" button next to the title, alongside the "Add Book" link the index page already had - following it opens edit.blade.php, pre-filled with the book's current values via the fallback in the shared partial. Change the title, upload an image, save - the show page reflects both immediately, and the catalogue's grid view shows the same new cover instead of the placeholder. Leave the title blank instead, and the same old()/x-input-error handling from last topic kicks in here too - a message under the field, every other value (and the file that's already attached) still there to fix and resubmit, exactly as it would on create.

One honest gap: uploading a new cover over an existing one doesn't delete the old file from storage/app/public/books - the column just points at the new one, and the old one sits there unused. Real applications usually clean that up explicitly; this app doesn't yet, because nothing has run long enough for the orphaned files to matter. Deleting a book entirely - and what that should mean for its cover image - is next topic's subject.
