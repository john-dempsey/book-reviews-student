Orientation: the domain model and stack

The book review catalogue's domain model, the Docker environment it runs in, and what this lesson will actually build.

Before any code changes, it's worth being able to answer two questions: what are we building, and what's already running underneath it. This page covers both, then lays out the rest of this lesson.

The domain model

The app is a book review catalogue, built around four things:

  • A User can write many Reviews.
  • A Book can have many Reviews — but at most one Review per User per Book. That's not just a rule the app remembers to enforce; it's backed by a unique constraint in the database itself, so it holds even if a bug elsewhere tries to violate it. You'll build that constraint in this lesson's migrations topic.
  • A Book can have many Authors, and an Author can have written many Books — a many-to-many relationship, which needs a join table (author_book) in between. If you've drawn an entity-relationship diagram for a many-to-many before, this is exactly that shape.
  • A real catalogue would usually give a Book many Editions (different ISBNs, publishers, print runs). This app doesn't — a book's edition details (ISBN, publisher, price, edition number) live directly on the books table, so every Book has exactly one implicit edition. That's a deliberate simplification to keep the schema to a size this course's six weeks can comfortably cover, not an oversight.

In short:

User ──< Review >── Book ──< author_book >── Author
        (1 per user            (many-to-many)
         per book)

One thing this model deliberately does not do yet: nothing about roles. Every registered user has exactly the same permissions — there's no "admin" who can edit any book, no distinction beyond "logged in" or not. That's authentication (proving who you are), which Breeze gives you later in this lesson. Authorization — what a given user is allowed to do — only shows up in a narrow, manual form in Lesson 4 (you'll only be able to edit or delete your own reviews), and the general-purpose version of it isn't built at all in this six-week block. If that sounds like it's punting on something, it is, on purpose — it's a deliberate boundary for what these six weeks cover, not a gap you're meant to work around.

The stack, and what's already running

If you haven't already worked through the First-time setup steps in this project's README.md, do that now — the rest of this lesson assumes docker compose up -d --build has been run at least once, composer install and npm install && npm run build have completed inside the workspace container, and php artisan migrate has run without error.

That setup brings up four Docker Compose services, defined in compose.yaml and the docker/ folder alongside it:

Service What it is URL
apache-php-container Serves the Laravel app http://localhost:8080
mysql-container MySQL 8, holding the app's database localhost:3306
phpmyadmin-container phpMyAdmin, for browsing that database http://localhost:8081
workspace-container A terminal for php artisan, composer, npm —

This is the same shape of environment you used last year, so none of it should be unfamiliar: one container serves the app, one runs the database, one gives you a browser-based way to look inside that database. The one addition is workspace-container — it doesn't serve anything itself, it's just a shell (docker compose exec workspace-container bash) with PHP, Composer, and Node installed, so you have somewhere to run command-line tools without needing them inside the container that's serving live traffic.

Right now, with first-time setup done, you should be able to see:

  • The Laravel app, at http://localhost:8080 — Laravel's own default welcome page. Nothing app-specific yet; that's what this lesson starts building.
  • phpMyAdmin, at http://localhost:8081 — log in and you'll find a book_reviews database already containing a handful of tables (users, sessions, cache, jobs, and a few others) that Laravel creates by default. No books, authors, or reviews tables yet — those come from migrations you're about to write.
  • The workspace, reachable only via docker compose exec workspace-container bash — no URL, since it isn't a web server. This is where every php artisan and composer command in this lesson gets run.

Where the Laravel app itself came from

The project in src/ already exists, so you won't run this yourself — but it's worth knowing what created it, because you'll see this command again on your own projects. laravel new . scaffolds a fresh Laravel project into the current directory, and asks a handful of setup questions along the way. This project answered:

  • No starter kit — no built-in auth scaffolding yet. That's what Breeze, installed separately later in this lesson, adds.
  • PHPUnit for testing, not the alternative Pest.
  • MySQL as the database, matching the mysql-container service above.

What you get back is a bare Laravel installation: the framework, its default folder structure, and three default migrations (for users, cache, and jobs) — but no Breeze, no app-specific models or migrations. Laravel does scaffold one model and one factory by default, though: User (app/Models/User.php) and UserFactory (database/factories/UserFactory.php), both generic and both there before you write a single line of app-specific code. That's exactly the state src/ is in right now — users, cache, and jobs tables, a User model, a UserFactory, and nothing yet for books, authors, or reviews — and exactly what the rest of this lesson builds on top of.

What this lesson does

By the end of this lesson, working from that bare starting point, you'll have:

  1. Installed Breeze, adding registration, login, logout, and password-reset views and routes — real authentication, not a stub.
  2. Written and run migrations for the full schema above: books, authors, the author_book pivot, and reviews, alongside Breeze's users migration.
  3. Written the Eloquent model classes for each of those tables, with the relationships between them (Book::authors(), Author::books(), Book::reviews(), and so on) — if you've written a hand-rolled Active-Record-style model class before, this will feel like a very close relative, not something brand new.
  4. Written this lesson's first tests, proving the schema and the relationships actually work.

A migration is a version-controlled PHP class describing one schema change — "create this table," "add that column" — rather than a change you'd hand-make in phpMyAdmin. Running php artisan migrate applies every migration that hasn't run yet, in order, so the database's structure lives in code and git alongside the models and tests that depend on it.
