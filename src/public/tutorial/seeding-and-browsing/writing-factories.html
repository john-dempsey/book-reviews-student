Writing factories

One factory per model - AuthorFactory, BookFactory, ReviewFactory - and the HasFactory trait that turns each model into something that can conjure realistic-looking rows on demand.

Every row you've created so far has been typed out by hand. The model tests from the last topic built a Book like this:

$book = Book::create([
    'title' => 'The Pragmatic Programmer',
    'year' => 1999,
]);

That's fine for proving a schema works - one or two rows, with values you chose because they made the test's point. It falls apart the moment you want twenty books that don't all look suspiciously identical, or just want something in the database to look at while building a page, without caring what its title actually is. A factory is a class that knows how to produce one plausible-looking row for a model, as many times as you ask for it.

Creating a factory

php artisan make:factory generates the skeleton:

php artisan make:factory AuthorFactory --model=Author

<?php

namespace Database\Factories;

use App\Models\Author;
use Illuminate\Database\Eloquent\Factories\Factory;

/**
 * @extends Factory<Author>
 */
class AuthorFactory extends Factory
{
    /**
     * Define the model's default state.
     *
     * @return array<string, mixed>
     */
    public function definition(): array
    {
        return [
            //
        ];
    }
}

An empty definition(), waiting to be filled in - the same shape as the $fillable array from the models topic, just generated into its own file in database/factories/ rather than typed into the model class itself. The @extends Factory<Author> comment above the class isn't required by PHP - it's a type hint for your editor, so autocompletion knows that AuthorFactory::new() deals in Author objects rather than some generic model.

One thing the generator doesn't do: wire the factory onto the model itself. Author, Book, and Review need a trait added before Author::factory() means anything -

use Database\Factories\AuthorFactory;
use Illuminate\Database\Eloquent\Factories\HasFactory;
use Illuminate\Database\Eloquent\Model;

class Author extends Model
{
    /** @use HasFactory<AuthorFactory> */
    use HasFactory;

    protected $fillable = [
        // ...
    ];
}
  • same opt-in instinct as $fillable: a model doesn't get factory support just for existing, it has to ask for it. Book and Review each get the same two lines, pointing at their own factory. User already had this - Breeze's install wired HasFactory onto it before this lesson touched anything.

Filling in the definition

definition() returns an array of column-name => value, exactly like the arrays you've been passing to Model::create() - the difference is every value here comes from Faker, a library that generates realistic-looking random data, via the fake() helper. AuthorFactory is the simplest one:

public function definition(): array
{
    return [
        'name' => fake()->name(),
        'image' => null,
        'bio' => fake()->paragraph(),
    ];
}

fake()->name() returns a plausible full name (a different one every call), fake()->paragraph() a plausible paragraph of prose. image is left null on purpose - nothing generates a real image file, and the column is nullable.

BookFactory leans on a few more of Faker's generators:

public function definition(): array
{
    return [
        'title' => rtrim(fake()->sentence(random_int(2, 5)), '.'),
        'description' => fake()->paragraphs(3, true),
        'year' => fake()->numberBetween(1950, (int) date('Y')),
        'image' => null,
        'isbn' => fake()->isbn13(),
        'publisher' => fake()->company(),
        'edition_number' => (string) fake()->numberBetween(1, 5),
        'price' => fake()->randomFloat(2, 9.99, 79.99),
    ];
}

Worth pausing on a couple of these:

  • fake()->sentence(2, 5) produces a short sentence like "Voluptas et fugiat." - it always ends in a full stop, which reads oddly as a book title, so rtrim(..., '.') strips it back off.
  • year is bounded between 1950 and this actual year (date('Y'), cast to an int) rather than a fixed upper limit that would quietly go stale - it always generates a plausible publication year, not a hardcoded one that ages badly.
  • edition_number is cast to a string with (string) because the column itself is a string in the migration (Part 1 keeps edition details as plain fields on books, rather than a separate editions table) - numberBetween() returns an int, and the factory's job is to match the column's actual type.

A factory that depends on other rows: ReviewFactory

A review doesn't make sense floating on its own - it belongs to a book and was written by a user. ReviewFactory reflects that:

public function definition(): array
{
    return [
        'book_id' => Book::factory(),
        'user_id' => User::factory(),
        'rating' => fake()->numberBetween(1, 5),
        'comment' => fake()->boolean(80) ? fake()->paragraph() : null,
    ];
}

book_id and user_id aren't Faker values - they're other factories, nested inside this one. Ask for Review::factory()->create() with nothing overridden, and Eloquent doesn't just leave those columns empty: it runs Book::factory() and User::factory() first, creates a brand new book and a brand new user to go with them, and only then creates the review pointing at both. That's a sensible default for a factory used on its own - it always produces a complete, valid row, never a review with a book_id pointing nowhere - even though it's rarely what you actually want once specific books and users already exist to attach reviews to instead.

comment shows a different kind of variation: fake()->boolean(80) returns true about 80% of the time, so most reviews get a written comment and some are left with just a star rating - null, since the column is nullable.

Using a factory

Every factory gives you the same handful of methods, regardless of which model it belongs to.

create() builds a model instance and saves it to the database straight away:

Author::factory()->create();

count() (or the shorthand of passing a number straight to factory()) makes several at once:

Book::factory()->count(3)->create();
Book::factory(3)->create();   // same thing

Overriding attributes - pass an array to create(), same as Model::create(), and only those keys are pinned; everything else still comes from definition():

Book::factory()->create(['title' => 'Dune']);

Handy when a test cares about one specific value (a known title to search for, say) but doesn't care what the rest of the row looks like.

make() is create()'s quieter sibling - it builds the model object with the same fake attributes but never saves it, so nothing touches the database:

$book = Book::factory()->make();   // in memory only, not in `books`

Rarely what you want for a book or author, since there's nothing to look at until it's actually saved - but worth knowing it exists, and that create() is really just make() plus a save() call, the same relationship your own Active-Record-style classes had between building an object and persisting it.

What's still missing

Every row created so far - in tinker, in last lesson's tests, and above - has existed one at a time, created because someone typed a command. Nothing yet produces a whole catalogue in one go: a fixed number of users and authors, books attached to the right authors, reviews attached to the right books and users, in the kind of quantity and shape a real (if fictional) book review site would actually have. That's the next topic's job.
